## 1. 观察范围与计时起点

同一组指标覆盖以下入口：

- `POST /v1/chat/completions`，流式与非流式；
- `POST /v1/responses`，流式与非流式；
- `POST /v1/messages`，流式与非流式；
- `/v1/responses` WebSocket 保留在 `legacy`，但记录为 `stream=true`，不计作 executor
  迁移命中。

观察窗口从下列条件全部满足后的第一条 orchestrator 指标样本开始，记录精确 CST 时间：

1. 新镜像已部署，`RELAY_ORCHESTRATOR_ENABLED=true`，SHA-256 allowlist 非空；
2. 至少一个真实内部 caller 使用 allowlisted token 调用当前主流 SSE 入口；
3. `micro_one_api_relay_executor_requests_total{execution_path="orchestrator"}` 增加；
4. 同 endpoint / stream 仍有 `legacy` 样本可作为对照。

只打开开关、只有 legacy 流量、Prometheus 未抓取或 orchestrator 样本为零，都不能开始计时。
窗口要求连续 7×24 小时；发布新 executor 代码、指标抓取中断超过一个抓取周期，或关闭 flag
后再开启，都要记录中断并重新确认起点。

## 2. 指标口径

| 指标 | 关键标签 | 用途 |
|------|----------|------|
| `micro_one_api_relay_executor_requests_total` | `endpoint,stream,execution_path,status,result` | 请求量、成功率、5xx、流终止和结算错误 |
| `micro_one_api_relay_executor_request_duration_seconds` | `endpoint,stream,execution_path` | 端到端 P95；SSE 包含完整连接生命期 |
| `micro_one_api_relay_executor_quota_outcome_total` | `endpoint,stream,execution_path,outcome` | Reserve / Commit / Release 生命周期 |
| `micro_one_api_relay_executor_failover_total` | `endpoint,stream,execution_path,result,reason` | 切换成功、耗尽和首个失败原因 |

`result` 的稳定值包括 `success`、`error`、`stream_error`、`quota_error`。流式 HTTP 已经写出
200 后仍可能发生协议截断或结算失败，因此不能只用 HTTP status 判断成功；7 天结论必须同时
检查 `result` 和 quota outcome。

## 3. 固定 PromQL

以下查询分别执行 `[24h]` 日检和 `[7d]` 总结；面板可把区间做成变量。

请求量与 terminal result：

```promql
sum by (endpoint, stream, execution_path, result) (
  increase(micro_one_api_relay_executor_requests_total[24h])
)
```

成功率：

```promql
sum by (endpoint, stream, execution_path) (
  increase(micro_one_api_relay_executor_requests_total{result="success"}[24h])
)
/
sum by (endpoint, stream, execution_path) (
  increase(micro_one_api_relay_executor_requests_total[24h])
)
```

5xx 比例：

```promql
sum by (endpoint, stream, execution_path) (
  increase(micro_one_api_relay_executor_requests_total{status=~"5.."}[24h])
)
/
sum by (endpoint, stream, execution_path) (
  increase(micro_one_api_relay_executor_requests_total[24h])
)
```

P95（SSE 表示完整流持续时间，不与非流式混合）：

```promql
histogram_quantile(
  0.95,
  sum by (le, endpoint, stream, execution_path) (
    rate(micro_one_api_relay_executor_request_duration_seconds_bucket[24h])
  )
)
```

quota outcome：

```promql
sum by (endpoint, stream, execution_path, outcome) (
  increase(micro_one_api_relay_executor_quota_outcome_total[24h])
)
```

failover 结果与原因：

```promql
sum by (endpoint, stream, execution_path, result, reason) (
  increase(micro_one_api_relay_executor_failover_total[24h])
)
```

## 5. 通过与回滚

7 天窗口通过需同时满足：

- 每个实际承载 allowlisted 生产流量的 endpoint / stream 均有 orchestrator 样本，不能用零样本判定通过；
- orchestrator 成功率不低于同 endpoint / stream 的 legacy 对照，且没有新增稳定错误类型；
- orchestrator P95 相对 legacy 不回归超过 20%；
- `quota_error=0`，没有重复 Commit、成功流 Release、截断流 Commit 或 reservation 卡单；
- failover exhausted 比例没有显著高于 legacy，reason 分布能够解释；
- billing 的 endpoint / stream 归因正确，usage 日志的 stream、channel / subscription account
  归因一致。

出现稳定性错误、计费不一致、P95 超线或协议兼容回归时，清空 allowlist 或关闭
`RELAY_ORCHESTRATOR_ENABLED`，所有请求立即回到 legacy。回滚不删除旧 handler，也不需要数据库
回滚；恢复观察时重新确认 §1 的起点。
