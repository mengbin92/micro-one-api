## 1. 执行摘要

项目已从“补核心能力”进入“稳定化和运营治理”阶段：9 个后端服务、React 管理端、订阅/计费/模型治理、Redis 多副本协同、可观测性和发布流水线均已形成完整骨架。v0.17 的工程收尾、性能基线与 jsonx 决策已经闭环；v0.18 又补上管理端资金路径幂等、MySQL matched-row 语义、全边缘 gRPC 指标和 relay 熔断配置。当前本地质量门禁全部通过，说明基线健康。

下一阶段不建议马上增加大功能。最值得优先处理的是三个“系统性风险”：

1. **刚修复的 Responses ↔ Anthropic `web_search` 兼容链路缺少跨路径契约矩阵**。当前 `develop` 比 v0.18.2 多 1 个测试提交 `a21970a`，应先收口为补丁发布，避免 release tag 与 develop 行为不一致。
2. **迁移体系缺少静态一致性门禁**。根 MySQL 迁移存在两个 `057_*` 文件，SQLite 迁移存在两个 `009_*` 文件；当前 runner 以完整文件名作为版本，因此暂不冲突，但序号重复会增加人工判断、跨方言映射和未来自动化的风险。
3. **测试分层仍有缺口**。默认单测主动排除所有 `internal/integration`，CI 也没有单独跑这些集成包；核心层测试较强，但 `platform/grpc/xgrpc` 等新基础设施包没有直接测试，前端 Playwright smoke 也未进入默认 CI。

建议把下一阶段定义为 **v0.19 稳定化阶段**：先完成 v0.18.3 收尾，然后以兼容性契约、迁移治理、CI 分层、发布可复现性为主线；账号级会话窗口和负载感知排队仍按指标触发，不主动实施。

## 2. 当前项目画像

### 2.1 产品与架构

- 定位：基于 Go Kratos 的多服务 AI API 网关与管理系统，兼容 OpenAI / Responses / Anthropic 等协议，并提供渠道、订阅、计费、日志、监控和通知能力。
- 服务矩阵：9 个可构建服务。
  - `relay-gateway`
  - `admin-api`
  - `identity-service`
  - `channel-service`
  - `billing-service`
  - `config-service`
  - `log-service`
  - `monitor-worker`
  - `notify-worker`
- 后端规模：122 个 Go package、609 个 Go 文件（其中 207 个测试文件）。
- 前端规模：`web/src` 下 118 个 TypeScript/TSX 文件、29 个 Vitest 文件、100 个测试用例。
- 数据层：MySQL 为主，提供 PostgreSQL / SQLite 方言工件；根迁移 74 个 SQL 文件，另有 PostgreSQL 16 个、SQLite 17 个 SQL 文件。
- 部署：Docker / Compose / Kubernetes 工件齐全；CI 以 9 服务 × amd64/arm64 共 18 个镜像构建任务验证多架构可构建性。

### 2.2 分层现状

仓库已经形成清晰的 DTO → service → DO/biz → repo interface → data/PO 分层契约，并通过 `scripts/check-architecture.sh` 守护。共享能力按用途拆在：

- `domain/`：订阅域、上游 provider 等跨服务领域能力；
- `platform/`：数据库、缓存、指标、gRPC、审计、安全、WebSocket 等基础设施；
- `pkg/`：`jsonx`、安全转换、文件与通配符等纯工具。

这套边界总体成熟，下一步应避免再做大范围目录重组。`log-service` 合并、grpc-gateway 替换等议题继续保留为触发式 ADR，不应成为近期主动工作。

## 4.3 P1：协议适配测试缺少显式的“兼容性矩阵” — ✅ 已完成（2026-08-12）

> 已落地：`internal/apicompat/compatibility_matrix_test.go`（OAuth/relay/adaptor 方向 8 cell）+ `internal/server/compatibility_matrix_test.go`（fallback + WebSocket 方向 5 cell），`Test*CompatibilityMatrix_Coverage` 断言期望坐标全部注册且无孤儿坐标；共享 fixture `matrix_fixtures_test.go` 固定输入形状；保留/转换/丢弃规则文档化于 `docs/design/v0.19-compat-matrix.md`。新增路径漏注册坐标会直接 CI 失败。

现状已有大量 `internal/apicompat` 和 `internal/server` 测试，但近期 web_search 问题连续经过三个递进提交才根治，说明测试更多按具体 bug 生长，尚未形成统一契约表。

建议至少建立以下矩阵：

| 方向 | 入口/路径 | 流式 | 非流式 | tools/history | 错误/中断 |
|---|---|---:|---:|---:|---:|
| Responses → Anthropic | OAuth adaptor | 必测 | 必测 | web_search 跳过、function tool 保留 | upstream 终止 |
| Responses → Anthropic | fallback | 必测 | 必测 | 同上 | fallback 错误映射 |
| Anthropic → Responses | relay response | 必测 | 必测 | server tool block 静默跳过 | block 中断/乱序 |
| Chat Completions ↔ Responses | adaptor/fallback | 必测 | 必测 | tool call/result round-trip | scanner/terminal event |
| WebSocket Responses | sticky/failover | 必测 | 不适用 | history/rebind | graceful drain |

重点不是增加重复测试数量，而是：

- 用 table-driven fixture 固定输入与期望输出；
- 明确“允许丢弃”的 provider 专有 block；
- 断言不产生 Codex 不支持的 item type；
- 流式与非流式必须共享同一语义断言；
- 新增 provider/tool 类型时，矩阵能直接暴露未覆盖组合。

## 4.4 P1：数据库迁移命名和跨方言一致性缺少门禁 — ✅ 已完成（2026-08-12）

> 已落地：`cmd/migrate-check` + `make migration-check`；`migrations/dialect-manifest.yaml`（allowlist、`auto_mirror_from_prefix: "072"`、not_applicable、ownership_exempt、historical_coverage）；ownership.yaml 补入 061 → billing；SQLite fresh + incremental 生命周期测试；`ci.yml` backend 增跑 `make migration-check`。遗留：MySQL/Postgres migration smoke 待 CI service-container 落地。

发现：

- 根迁移同时存在：
  - `057_add_plan_snapshot_to_payment_orders.sql`
  - `057_create_subscription_account_quota_reset_runs.sql`
- SQLite 同时存在：
  - `009_add_per_bucket_cost.sql`
  - `009_clean_orphan_model_mappings.sql`
- runner 当前使用完整 basename 作为 `schema_migrations.version`，所以不会直接主键冲突；但注释和操作习惯又强调“数字前缀排序”，容易让维护者误以为前缀唯一。
- MySQL / PostgreSQL / SQLite 的历史编号并非一一对应，且文件数量差异大，当前没有自动 lint 证明“该有的迁移都有、允许的差异都有说明”。

建议新增 `make migration-check` 并纳入 CI：

1. 检查每个方言目录内部是否存在重复数字前缀；
2. 历史重复项先进入 allowlist，不做危险重命名；
3. 新增迁移禁止再产生重复前缀；
4. 检查 `ownership.yaml` 引用的文件全部存在，且归属合法；
5. 检查 release 后新增 schema 变更是否同步覆盖 MySQL/Postgres/SQLite，或在 manifest 中显式标记“不适用”；
6. 增加 SQLite fresh install + incremental upgrade 自动测试；PostgreSQL/MySQL 保留 CI service-container smoke 或预发门禁。

说明：不要直接重命名已经在生产 `schema_migrations` 中登记过的历史文件，否则会被 runner 当成新迁移。若要统一编号，必须先设计 alias/rename migration 和兼容策略。

## 4.5 P1：集成测试被默认门禁整体排除 — ✅ 已完成（2026-08-12）

- 建立 `tools.go` 或集中版本变量；

- 将前端 Node/npm 版本也在仓库中显式固定（如 `.nvmrc` / `engines`），与 CI Node 24 对齐。

## 4.10 P3：触发式功能继续延期 — ✅ 准入评估完成（2026-08-13），维持触发式

> 已评估：五大议题逐项核对触发条件（证据详见 `docs/design/v0.19-p3-gate-assessment.md`）——
> 表分区（logs 13MB / ledgers 24MB vs 1GB/1000万行阈值）、会话窗口统一（无 Claude 多账号池）、
> 负载感知排队（账号池未饱和、熔断 trips=0）、log-service 合并（无成本数据）、
> grpc-gateway 迁移（relay 为唯一外部 REST facade）——**全部未达立项阈值**。
> 同时落地 **P3-0 触发条件可观测化**：relay HTTP 入口请求级指标（复用既有
> `micro_one_api_http_requests_total` / `..._request_duration_seconds`，
> `platform/middleware/http_metrics.go` + wire 最外层挂载 + 单测），使
> 「502/429 持续阈值」「入口延迟」可 PromQL 直接查询。

以下议题目前没有证据需要主动启动：

- 账号级更复杂会话窗口统一；
- 负载感知排队；
- log-service 合并为组件；
- 全面切换 grpc-gateway；
- `logs` / `billing_ledgers` 分区。

触发条件沿用现有决策：容量、延迟、失败率、运营成本或多 backend REST facade 需求达到明确阈值后再开 ADR。尤其分区目前表规模远低于 1 GB / 1000 万行阈值，且 `billing_ledgers` 仍有唯一索引前置约束。
