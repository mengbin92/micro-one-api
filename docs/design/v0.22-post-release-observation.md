## 3. 最终决策

按 §2 预设的三选一口径（PASS / PATCH / HOLD），最终结论为：

**PASS —— 无 v0.22 引入的生产回归，进入 v0.23 executor staging。**

依据：

1. **四个观察特性面全程零回归**：凭证加密与启动校验（窗口内无 decrypt / encryption
   key / 缺失 DSN/JWT / Redis 降级告警）、请求体分级限额（413 全程为 0，无日志
   命中）、批量可靠性（billing 关键对账项全程为 0，ledger↔claim 31,718 行完整
   对齐，异步队列零堆积）、前端错误兜底（无 RouteErrorFallback 或用户侧反馈异常）。
2. **窗口内暴露的缺陷均不属 v0.22.0 回归且已闭环**：Responses fallback、订阅模型
   探测（08-20 热修）、OAuth adaptor SSRF（既有安全缺口）、Kimi K3 参数（上游
   规则变更）、价格键大小写（既有精确匹配语义）、CC Switch/Claude 兼容、
   policy rejection 熔断误判（上游将业务策略拒绝编码为 HTTP 500）——已分别由
   08-20 热修镜像与 v0.22.1–v0.22.3 修复上线；v0.22.3 部署后 15.5 小时内仅
   1 次孤立 500，无 502/503/504、无熔断跳闸、无对账异常。
3. **口径限制**：九服务全为纯 v0.22.0 的状态只维持到 08-20 10:39/11:55（自部署
   约 20–21.5 小时，自初始快照仅约 1.3–2.6 小时），其后窗口由热修镜像与
   v0.22.1–v0.22.3 演进版本接替，48 小时边界复核在演进版本上完成。这弱化了对
   v0.22.0 本体的覆盖强度，但第 1 条的全窗口证据不受影响——四个特性面的代码自
   08-19 起未被回退，其相关指标在版本演进前后均为零异常。

遗留跟进（不阻塞 PASS）：

- `d5c3a3c`（订阅扣费避开空钱包）已提交未部署：线上 billing 镜像构建于该提交
  之前。建议随下一次发布窗口部署，并复核部署后 `/v1/responses` 的 402 分布变化。
- 既有对账历史差异（每次运行 3 account / 7 channel / 1 receivable）贯穿整个窗口
  无变化，维持“v0.22 部署前已存在”的定性，另立事项跟踪，不与 v0.22 观察绑定。
