## 1. 背景与目标

M6 实施(2026-08-05,`5759b82`)用 InTx 行锁解决了订阅行的并发覆盖,但明确记录边界:admin 层钱包扣款
(`PurchaseSubscription` RPC)是行锁事务**之前**的独立调用,并发升级/购买请求仍会各自成功扣款——双扣款是
当前仓库**唯一已知的资金正确性开放项**。

本设计把该开放项收敛:**全部资金写路径具备请求级幂等,并发重复请求不产生第二笔资金变动**。

已拍板前提(roadmap §3 P0):
- 方案 B(DB 唯一键)为主,方案 A(幂等中间件)补充评估;
- 覆盖范围为**全部资金写路径**(购买/升级/降级/续费/切换/充值/退款等),不限于购买路径。

## 2. 资金写路径清单(梳理结果)

|---|------------|--------------|---------|-------------|------|

## 3. 方案候选对比与决策(roadmap §3 P0 原文同步)

### 3.1 候选一:方案 A — 复用现有幂等中间件(Redis 存储)

**现状**:`platform/middleware/idempotency.go` 已实现(`Idempotency-Key` + Redis 缓存 + 本地 inflight 锁 +
分布式租约),挂在 relay-gateway 路由(`cmd/relay-gateway/wire.go:363`),admin-api 未接入。

**做法**:admin-api 对 `POST /subscriptions/purchase` 等写操作启用幂等中间件,客户端(admin 前端)携带
幂等键(如 `Idempotency-Key` 请求头),同键请求返回首次结果。

**优点**:
- 复用现有 Redis 基础设施,改动面小;
- 与 relay 行为一致(同一 header 协议、同一响应缓存语义)。

**风险**:
- 幂等键生成与传递协议需前端配合;
- 中间件当前面向 relay 的响应缓存语义,需核对是否适配 admin 的业务响应;
- 资金正确性依赖 Redis 可用性:TTL(24h)过期后同键请求重新执行;Redis 抖动/降级时中间件放行(详见 §6)。

### 3.2 候选二:方案 B — DB 层幂等(唯一键 + 去重)

**做法**:在 `subscription_orders`(或等价表)上对 `(user_id, request_id)` 建唯一约束,购买事务内
INSERT,冲突即返回已有结果。

**优点**:
- 不依赖前端传键,服务端天然幂等;
- 与 H10(active 唯一约束)既有模式一致。

**风险**:
- 需新增迁移 + 请求 ID 生成规范;
- 适用范围限于购买路径(需评估是否扩展至充值/退款等全部资金写路径)。

### 3.3 对比与决策(2026-08-10 用户拍板)

| 维度 | 方案 A(中间件) | 方案 B(DB 唯一键) |
|------|---------------|------------------|
| 幂等保证位置 | HTTP 层(Redis 缓存响应) | DB 层(唯一约束拒绝第二次写) |
| 资金正确性强度 | 依赖 Redis 可用性与 TTL | 数据库硬约束,不依赖外部组件 |
| 前端配合 | 需要(传 `Idempotency-Key`) | 需要(同协议);无键时退化为 auto 键(不幂等) |
| 迁移 | 无(复用现有中间件) | roadmap 原文:需新表/新索引;设计评审收敛为**零迁移**(见 §5.1) |
| 与既有模式契合 | relay 同款 | H10 / 072 唯一约束同款 |
| 重复请求体验 | 返回首次结果(replay) | 返回 409 冲突错误 |

**决策(roadmap 附录 B #1 已拍板)**:方案 B 为主(DB 层幂等,服务端天然幂等,契合 H10 唯一约束先例),
方案 A(幂等中间件)作为补充评估。

**评审落地修正**:roadmap 原文建议在 `subscription_orders`(或等价表)上新建唯一约束;设计评审发现仓库
**无 `subscription_orders` 表**,且 `billing_ledgers` 已存在全局唯一的 `ledger_dedupe_key` 索引(迁移 `045`),
同时实测发现 legacy 键冲突 bug(§4.1)——落点收敛为**复用 `ledger_dedupe_key` 显式键**,零新表零迁移,
并顺带修复 legacy bug。方案 A 的详细评估见 §6。

## 4. 现状诊断:一个必须一并修复的既有 bug

### 4.1 扣款 ledger 的 legacy dedupe key 冲突(实锤)

`BillingUsecase.PurchaseSubscription`(billing.go:1471)写扣款 ledger 时**未显式设置
`LedgerDedupeKey`**,`CreateLedgerInTx` 回退到 `legacyLedgerDedupeKey`:

```go
// data/ledger_repo.go:84
if ledger.ReferenceID != "" {
    return fmt.Sprintf("%s:%s:legacy", ledger.ReferenceID, ledger.Type)
}
```

PurchaseSubscription 的 ReferenceID = `groupID`,Type = `subscription`,因此每笔扣款 ledger 的 dedupe key
固定为 **`{group_id}:subscription:legacy`**——**不含 user_id、不含 request_id**。

而 `billing_ledgers.ledger_dedupe_key` 是**全局唯一索引**(迁移 `045`,`idx_ledger_dedupe_key`)。实测验证
(sqlite 内存库复现,临时测试已跑通后移除):

```
INSERT ... ("B",-100,0,900,"subscription","5",...) ledger_dedupe_key="5:subscription:legacy"
→ UNIQUE constraint failed: billing_ledgers.ledger_dedupe_key
```

**即:同一 group 的购买扣款只能成功一次。** 后果:
- 不同用户购买同一 group:第二笔扣款直接失败(用户 B 无法购买 group 5);
- 同用户续费/二次购买同 group:同样失败。

这是现存的生产资金正确性缺陷,本次方案 B 的落点恰好同时修复它(显式键区分 user_id/request_id)。

### 4.2 退款、完成购买已有幂等(不重复造轮子)

- 退款:`MarkOrderRefunded` 行锁事务 + reversal ledger 显式 dedupe key `{trade_no}:refund:{cost_source}`(refund.go 注释),重复回调为 no-op;
- 完成购买:M10 的 `MarkOrderAssetIssued` 原子 claim,同一 trade_no 只能 claim 一次。

这两条路径已在 DB 层幂等,本次不修改。

## 5. 方案 B 设计(落点确定)

### 5.1 核心思路:扣款/充值 ledger 显式携带 (user_id, request_id) 幂等键

复用 `billing_ledgers.ledger_dedupe_key` 的**全局唯一索引**作为去重闸门:

- 资金变动(扣款/充值)ledger 写入时**显式设置** `LedgerDedupeKey`(不再走 legacy 回退);
- 键格式:`{action}:{user_id}:{request_id}`,与 legacy 格式(`{ref}:{type}:legacy`)天然区分,互不冲突;
- 并发同键第二次 INSERT → 唯一索引冲突 → **整个事务回滚**(`UpdateBalanceInTx` + `CreateLedgerInTx`
  同一事务)→ 不产生第二笔资金变动;
- 不同请求/不同用户 → 键不同 → 正常执行。

**零新表、零新迁移**:`idx_ledger_dedupe_key` 已存在,`ledger_dedupe_key` 列宽 VARCHAR(160) 足够。

### 5.2 键格式与长度约束

```
purchase:{user_id}:{request_id}     // 购买/升级扣款(type=subscription)
topup:{user_id}:{request_id}        // 充值(type=recharge)
```

- `user_id` 为字符串形式(与 ledger.user_id 一致,proto 本来就是 string);
- `request_id` 规范:**1–100 字符,ASCII 可见字符**,由客户端生成并在重试时复用;
- service 边界校验:超长/含控制字符的 request_id 直接 400 拒绝(防键膨胀/注入);
- 列宽检查:`purchase:`(9) + user_id(≤64) + `:` + request_id(≤100) ≤ 174 < 160?——**不满足**,
  因此约束 user_id 前缀截断:`{action}:{user_id截断至48}:{request_id≤100}` = 9+48+1+100 = 158 ≤ 160 ✅。
  实现上对 `request_id` 做 sha256 摘要(32 hex)再拼接可彻底避免长度问题,但可读性下降;
  采用**截断 user_id + 限制 request_id 长度**的可读方案,见 §8 决策记录。

### 5.3 request_id 生成与传递链(协议)

| 层 | 行为 |
|----|------|
| 客户端 | 写操作请求头 `Idempotency-Key: <key>`(与 relay 幂等中间件同协议)。前端在**发起时生成一次**,重试/双击复用同一 key。 |
| admin HTTP | 读 `Idempotency-Key` 头 → 透传到 service 层;无头时传空串。 |
| admin service | 校验/透传;空串时内部生成 `auto:{uuid}`(保证**永不撞 legacy 键**,即修复 §4.1 bug;但不提供幂等——无键 = 无幂等保证,兼容旧客户端)。 |
| billing RPC | `PurchaseSubscriptionRequest` / `TopUpQuotaRequest` 新增 `request_id` 字段(proto 变更,`make api` 重新生成)。 |
| billing biz | `PurchaseSubscription` / `TopUpQuota` 签名加 `requestId` 参数 → ledger 显式 dedupe key。 |

不依赖前端改造即能修复 §4.1 bug(无键时走 `auto:{uuid}`);前端接入 `Idempotency-Key` 后获得完整幂等。

### 5.4 冲突返回语义

- billing biz 检测到唯一冲突(MySQL/Postgres 错误码 1062/23505)→ 返回 `ErrDuplicateRequest`
  (biz 层新增 typed error);
- **错误传播链(已实现,2026-08-10 review 修复)**:billing service 将 `ErrDuplicateRequest`
  映射为 gRPC `codes.AlreadyExists`(而非吞入 `Success:false`);admin service 对
  `codes.AlreadyExists` 透传(不吞入业务失败响应);admin HTTP 层
  `httpStatusForAdminError` 将 gRPC 语义映射为 **409 Conflict**——
  `writeSubscriptionResponse` / `writeServiceResponse` / `handleChangeSubscription`
  三处已接入,响应体含可读错误消息;
- **不做"返回首次结果"**:重复请求返回冲突错误,由客户端决定是否重试/刷新。
  首次结果的 replay 语义由方案 A(中间件)补充(见 §6),二者职责分离:
  **DB 保证资金正确性,中间件改善重复请求体验。**

### 5.5 覆盖范围映射

| 路径 | 改动 |
|------|------|
| #1 购买 | `PurchaseSubscription` / `PurchaseSubscriptionPlan` 加 requestID;扣款 ledger 显式键 |
| #2 升级 | `ChangeSubscription` 差价扣款同一路径(内部同样调用 billing.PurchaseSubscription,自动获得幂等) |
| #4 充值 | `TopUpQuota` 加 requestID;recharge ledger 显式键 |
| #3 支付单 | 依赖 admin 层方案 A 中间件(见 §6),不新增 DB 结构;评审结论:重复建单无资金损失,接受现状 + 记录 |
| #5 #6 | 已有幂等,不改 |

### 5.6 迁移设计

**无数据库迁移。** 理由:
- 唯一索引 `idx_ledger_dedupe_key` 已存在(迁移 `045`);
- 新键格式与 legacy 键格式不重叠,历史行无需 backfill;
- 唯一新增的 DB 行为是"同 (user_id, request_id) 扣款 ledger 冲突回滚",由新代码写入的显式键触发。

回滚方案(发布说明要求):代码回退即恢复 legacy 行为(需注意 legacy 键冲突 bug 随之回归,随代码一并回退,
无数据残留)。

## 6. 方案 A 评估(补充)

**现状**:`platform/middleware/idempotency.go` 已实现(`Idempotency-Key` + Redis 缓存 + 本地 inflight 锁 +
分布式租约),挂在 relay-gateway(`cmd/relay-gateway/wire.go:363`),admin-api 未接入。中间件行为要点
(与 relay 一致,`platform/middleware/idempotency.go`):
- 仅对 POST/PATCH/PUT/DELETE 生效,`GET/HEAD/OPTIONS` 直通;
- 无 `Idempotency-Key` 头时直通(不缓存、不拦截);
- 键按 (bearer token hash + method + path + key) 复合哈希,跨用户/跨接口不可串用(review M2);
- 同键并发:本地 inflight 等待 + Redis 分布式租约双保险(review Medium #6);
- 仅缓存 2xx 响应;响应体 > `MaxCachedBodyBytes`(1 MiB)不缓存;
- 命中缓存回放时写 `Idempotency-Replayed: true` 响应头。

**作为 B 的兜底 / 非 DB 场景补充的价值**:

| 维度 | 评估 |
|------|------|
| 资金正确性 | ❌ 不能作为唯一保证:Redis TTL(24h)过期后同键请求重新执行;Redis 抖动/降级时中间件放行;多实例 inflight 锁依赖 Redis 可用性 |
| 重复请求体验 | ✅ 同键重复请求返回**首次成功响应**(replay),避免 409 冲突令客户端困惑;与 Stripe 等主流幂等协议一致 |
| 与 B 的关系 | **互补**:B(DB 唯一键)是资金正确性的最终兜底;A 是 HTTP 层的体验增强。二者共享同一 `Idempotency-Key` 协议,可叠加 |
| 成本 | admin 挂中间件 + 前端传键 + 响应序列化适配;中间件当前面向 relay 的响应缓存语义,admin 业务响应较小(≤1MiB 上限内)可直接复用 |

### 6.1 接入设计(若作为后续增强实施)

- **挂载位置**:admin HTTP server 路由中间件链(与 relay-gateway `wire.go:363` 同款
  `NewIdempotencyMiddleware(redisClient, cfg).Handler`),可在资金写路由或全路由启用;
- **配置**:复用 relay 的 `Bootstrap.Idempotency` 配置节(`Enabled` / `Ttl`),Header 固定
  `Idempotency-Key`(与 B 协议一致,无需前端两套键);
- **与 B 叠加语义**:中间件命中缓存 → 直接回放首次结果(体验);未命中(首次请求 / Redis 抖动 / TTL 过期)
  → 请求落到 B,DB 唯一约束兜底拒绝重复写(正确性)。二者共享同一键,前端无需区分;
- **边界**:响应体 > 1 MiB 不缓存、4xx/5xx 不缓存(review M2)——资金错误响应不会长时间被回放。

**决策:本次 P0 实施方案 B(资金正确性兜底,必须);方案 A 作为 v0.18 后续增强立项(改善重复请求 replay 体验),
不并入 P0 主体。** 理由:资金正确性由 DB 唯一键保证即可闭环;中间件接入需要前端配合与响应适配,
收益是体验而非正确性,单独立项按需推进(触发条件:P0 上线后观测到前端重试导致 409 噪音)。

## 9. 风险与边界

- **R1**:`request_id` 由客户端控制,恶意客户端可故意复用他人键制造 409——仅影响自身请求,不产生资金变动;
  键内嵌 user_id,跨用户不冲突。可接受。
- **R2**:无键旧客户端获得 `auto:{uuid}` 键,并发双击仍可能双扣款(与现状相同)——幂等保护需要客户端配合,
  文档注明前端接入 `Idempotency-Key` 是完整防护的前提。
- **R3**:`ledger_dedupe_key` 唯一索引冲突在 MySQL 默认事务隔离下,并发 INSERT 由唯一索引原子裁决,
  无死锁;Postgres 同。sqlite 测试环境行为一致(唯一约束同样生效)。
- **R4**:`ChangeSubscription` 的补偿退款(TopUpQuota)不携带原 request_id,退款与扣款键不同——正确,
  补偿退款不是重复请求,不应被幂等拦截。
