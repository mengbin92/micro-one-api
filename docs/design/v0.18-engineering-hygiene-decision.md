## 1. C2 — RowsAffected==0 边界（修复，方案 C：clientFoundRows）

### 问题

仓库 10+ 处 `RowsAffected == 0 → ErrXxxNotFound` 判断（identity 2 处、channel
~9 处、billing 若干）。MySQL 默认 UPDATE 返回 **changed rows**（值未变化的行
不算），因此**幂等更新**（如 `ChangeModelStatus` 重复设置相同 status、`UpdateModel`
写入相同值）会返回 RowsAffected=0 → 误判 Not Found。生产已暴露此模式
（channel model 状态/模型更新路径）。

### 决策（2026-08-11）

**采用方案 C：MySQL DSN 全局启用 `clientFoundRows=true`**（matched-rows 语义），
一处修复所有此类判断。修改 `platform/database/xdb`：共享 `withClientFoundRows(dsn)`
助手同时注入到两条 MySQL 打开路径——gorm 路径 `openMySQL` 与 `*sql.DB` 路径
`OpenSQLWithPool`（后者服务 admin system_options 与 migrate CLI；review 2026-08-11
补盲点，避免未来任何经 `OpenSQL` 的 `RowsAffected==0` 判断重新踩坑）。

**影响评估**：

| 使用点 | clientFoundRows 后语义 | 影响 |
|--------|------------------------|------|
| `RowsAffected==0 → NotFound` 判断（10+ 处） | 0 = 无匹配行（真 not found） | ✅ 修复误判 |
| 批量 affected 计数（`BatchUpdateModelStatus`/`BatchDelete` 返回 affected） | matched 数（含未变化行） | ✅ 更符合"处理了 N 个"的用户预期 |
| DELETE 的 RowsAffected | 不受影响（DELETE 恒为 matched） | 无 |
| sqlite 测试环境 | 不受影响（参数仅 MySQL） | 无 |

**守护**：`xdb.TestOpenMySQLForcesClientFoundRows`（DSN 参数 + 往返解析断言）与
`xdb.TestWithClientFoundRowsSharedByBothMySQLPaths`（共享助手注入两条路径 +
`OpenSQLWithPool` 接受改写 DSN）。

> 未选方案：逐处显式 SELECT 确认（改动 10+ 处、成功路径多一次查询）；
> 维持现状（文档化）——误判会随幂等操作产生真实 not-found 错误，不可接受。

## 2. C4 — 日志分区启用条件（触发阈值后启用）

### 结论（2026-08-11 生产实测）

| 表 | 规模 | 可分区性 |
|----|------|---------|
| `logs` | 13 MB / 22.9k 行 | ✅ 无全局唯一键，可直接按月分区 |
| `billing_ledgers` | 24 MB / 22.7k 行 | ⚠️ 唯一索引 `idx_ledger_dedupe_key(ledger_dedupe_key)` 不含分区列 created_at → 分区 DDL 报 1503 |

**当前不启用**（规模远低于阈值）。**触发阈值**（任一）：单表 ≥ 1 GB 或 ≥ 1000 万行，
或出现相关慢查询，或产生按月清理需求。

**启用前置**：`billing_ledgers` 需先解决唯一索引约束（重建为
`UNIQUE(created_at, ledger_dedupe_key)`，分区列前置；或该表暂不分区、仅 logs 分区）。

**机制已就绪**：`platform/database/partition`（自动建/删分区），
log-service 与 billing-service 均有 `partition.enabled` 开关（默认关，env
`PARTITION_ENABLED`），无代码改动。启用步骤见
`docs/runbooks/table-partitioning-runbook.md`。

## 3. C5 — Prometheus 服务内部指标采集（根因：埋点缺失）

### 诊断（2026-08-11 生产 Prometheus）

| 指标（BASELINE 查询集） | 生产现状 | 根因 |
|--------------------------|---------|------|
| `micro_one_api_dependency_grpc_latency_seconds` | 无数据 | `ServiceDependencyLatency` 注册但**从未被 Observe**（无 gRPC 客户端拦截器埋点） |
| `micro_one_api_billing_commit_duration_seconds` | 无数据 | `BillingCommitDuration` 注册但**从未被 Observe**（仅 reserve 有 async 埋点） |
| `micro_one_api_resilience_circuit_breaker_state` | 无数据 | `UnaryClientInterceptor`（熔断埋点）已实现但**未 wire 到任何 dial 点** |
| `micro_one_api_routing_selection_duration_seconds` | ✅ 有数据 | P50 7.6ms / P95 10ms / P99 22ms（channel，5m rate） |
| `micro_one_api_cache_hits_total` | ✅ 有数据 | auth 缓存 L1 79.6% / L2 15.9% / Miss 4.5% |

> 结论：缺指标的根因是**代码埋点缺失**，非采集配置问题——这也是 P3.1 遗留
> "N/A — not scraped" 的真实原因（指标从未产生数据）。

### 修复（代码）

1. **billing commit/reserve 埋点**：
   - sync commit：`BillingService.CommitQuota` 的**同步分支**（async enqueue 分支提前
     return，不产生 sync 样本；async 由 worker 自埋）——review 2026-08-11 修正：sync 埋点
     **不在** `CommitQuotaWithUsage` 顶层（该函数被 async 管线 `CommitQuotaWithUsageAndSplit`
     委托，顶层埋点会导致 async 样本同时写入 sync 标签的双重计数）；
   - async commit：`AsyncBillingUsecase.runCommitPipeline` Observe("async")；
   - sync reserve：`ReserveQuota` 入口 Observe("sync")（async 已有）。
2. **gRPC 延迟埋点**：新增 `platform/grpc/xgrpc.UnaryClientMetricsInterceptor`，
   接入 admin-api 的 identity/channel/billing 三个 dial 点。
3. **熔断拦截器 wire**：`platform/grpc/resilience.UnaryClientInterceptor` 已实现，
   未 wire（**已知遗留**，见下）。
