## 4. P0 — Responses 上游 4xx 误报 502

### 4.1 生产诊断记录（2026-09-03）

- 生产所有容器保持运行，MySQL / Redis 健康；channel 1 在故障时段内健康探测成功、连续
  失败为 0。线上主机到 `https://gpunexus.chengfangtech.com/api/v1` 的 DNS、TLS 和 HTTP
  连通正常。
- 通过 channel-service 内部 gRPC 解密链路取得 relay 实际使用的凭据后，向同一上游发送
  `GLM-5.3`、`max_tokens=1` 的非流式最小请求，返回 HTTP 200 且模型回显为 `GLM-5.3`。
  因此排除数据库密文、凭据失效、模型 ID 大小写、基础地址和 channel 整体不可用。
- `GLM-5.3` 在 17:17 CST 前持续成功；17:45:28–17:47:30 CST 出现 30 条相同估算量
  （6,602）的 released reservation，对应 selection 结果均为 `client_error`。相邻时段
  `kimi-k3` 也出现 7 条 released reservation，而其他模型仍有成功流量，说明触发条件是
  特定 Responses 请求内容/上下文，不是单一模型故障。
- 正常兼容链路中，上游原生 `/responses` 返回 405，relay 会降级到 `/chat/completions` 并
  成功。故障请求没有产生 `responses to chat fallback failed` 记录，结合 `client_error` 可
  确认真正的上游响应是一个不在当前 fallback 白名单内的 4xx；现有终止分支没有记录原始
  `upstream_status`，因此不能把 413 / 415 / 422 / 403 中的任一状态写成既定事实。
- 客户端最终看到 502，是因为 `mapUpstreamError` 只显式保留 400、402、429、502、503、504，
  其他状态全部进入 `default → 502`。这是错误呈现和不可观测性的直接根因；上游 4xx 的原始
  请求级触发原因需在补日志后用同一失败请求复现确认。

### 4.2 修复边界

修复归属 `relay-gateway`，当前证据不支持修改 channel-service、模型注册、数据库记录或线上
凭据。最小改动范围：

1. 在 Responses 原生调用作 fallback 决策前，以及最终返回错误前，记录低基数
   `upstream_status`、endpoint、stream、execution path 和脱敏后的错误类别；禁止记录
   Authorization、请求正文或完整上游错误正文；
2. 把对外状态策略改成显式矩阵，不再用 `default` 吞掉所有未知 4xx。413 明确表示请求过大；
   415 / 422 根据兼容语义映射为客户端请求错误；上游 401 / 403 仍需与客户端鉴权失败区分，
   不直接把上游凭据状态伪装成客户端 Token 401；
3. 仅在证明确属“上游不支持 Responses、但可安全转为 Chat”时扩展 415 / 422 fallback；413
   不重试、不 fallback。保留现有 400 / 404 / 405 / 501 / 502 / 503 行为；
4. 为普通/流式 `/v1/responses` 覆盖 401、403、413、415、422，断言 fallback 决策、最终
   HTTP 状态、selection result、reservation release 和日志脱敏一致；再用生产等价失败形状
   做一次受控回归。

### 4.3 实现记录（2026-09-04）

- 对齐同级 `sub2api` 的确定性客户端错误边界：请求错误不再统一伪装成可重试 502，
  并保留经过脱敏的 OpenAI `type` / `code` / `param` / `message`；上游 401 / 403 仍显式
  映射为 502，避免与客户端 Relay Token 鉴权失败混淆。
- 状态矩阵新增 413→413、415 / 422→400；413 不进入 fallback，415 / 422 仅在

  原有 400 / 404 / 405 / 501 / 502 / 503 fallback 行为保持不变。
- Responses 原生请求在 fallback 决策前和最终错误返回前都会记录 `upstream_status`、
  endpoint、stream、execution path、phase 和低基数错误类别；日志不再携带请求头、
  请求正文或上游错误正文，fallback 成功/失败日志也只记录状态和类别。
- 普通与流式矩阵覆盖 401、403、413、415、422，并断言上游路径、最终 HTTP 状态、
  selection result、reservation commit/release 和日志脱敏。`go test ./internal/server

### 5.2 灰度步骤

1. `BILLING_CANONICAL_USAGE_MODE=observe`，producer gate 关闭，验证旧 producer / 新
   consumer 兼容；
2. 小流量开启 `RELAY_CANONICAL_USAGE_PRODUCER`，连续观察至少 48 小时；
3. 用固定 SQL 和指标确认 `ambiguous=0`、`cost_mismatch=0`、unexplained delta=0、
   source / upstream model 覆盖率 100%，且 v1 priced 行没有非法 canonical 静默 fallback；
4. 先对 Kimi / Z.AI / MiniMax 明确范围切 `charge`，一次只扩大一个来源；
5. 小范围 charge 稳定并完成供应商账单抽样对账后，再决定全量；

## 6. P1 — 历史账务只读审计

历史 ledger 缺少足够协议证据，不能根据 `cache_read_tokens > prompt_tokens` 或
`total_tokens` 数值关系自动退款/追扣。本阶段只补安全的审计入口：

1. 在既有 `scripts/reconcile` 体系中增加只读报告，按 `verified / candidate / unknown`
   分类；
2. 报告列出原 ledger、source、upstream model、usage contract、parse status、五桶成本、
   pricing hash、候选差额和证据来源；
3. 默认不写数据库、不调用 billing RPC；输出确定性 CSV/JSON 供人工与供应商账单核对；
4. 只有 `verified` 且获得显式审批的记录，才在后续独立任务中生成幂等 reversal 草案；
5. 任何冲正都新增 reversal ledger，禁止原地修改 consume ledger；订阅吸收与钱包部分按
   原请求归属分别处理。

验收标准：

- [x] 默认模式兼容生产 MySQL 的只读账号，代码路径没有写操作（隔离实库 SELECT-only 验证）；
- [x] fixture 覆盖 OpenAI subset、Anthropic exclusive、ambiguous 和证据不足四类；
- [x] 同一输入重复运行输出稳定，不产生 ledger 或外部副作用；
- [x] 自动冲正不属于 v0.27.0 发布前置。

**2026-09-09 实现记录**：

  支持 CSV 和离线 fixture，未接入 billing RPC 或任何写入/冲正入口。
- verified 要求完整 v1 usage 审计事件、来源和 SHA-256 校验通过的冻结价格快照；
  legacy/estimated/ambiguous 或证据不足保留 candidate，缺 usage、非法/冲突证据、
  窗口截断同请求的拆分账本记为 unknown。没有快照的旧价格及差额留空，不反推当前价格。
- 报告按请求合计原实扣，保留订阅与钱包各自原 ledger、支付金额、订阅归属和五桶证据；
  差额不重复计算或自动分摊。复算遵循 Go float64 逐桶舍入、最低 1 quota 与冻结的

  验证默认数据库入口：报告与离线 fixture 一致、两次输出一致、半开窗口不误算部分请求、
  ledger 行数及金额保持不变，写权限验证返回拒绝。相关 race、go vet 和 `make verify`

  未修改 K3 charge 或 executor 配置。运行方式、字段和证据限制见
