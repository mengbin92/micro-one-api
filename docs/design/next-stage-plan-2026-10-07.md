## 2. 规划依据与顺序

近期连续四个补丁集中在 IAM 切换后的跨服务调用、字段展示、本人入口和交互。这支持优先补齐**既有关键业务路径的持续验收**，尚不足以说明需要重写权限架构。

静态核对发现两个具体门禁缺口：`make rbac-contract-check` 已存在，但 `make verify` 与 `.github/workflows/ci.yml` 没有显式调用；`TestIAMCRealBrowserMatrix` 默认跳过，只有 `IAM_C_PLAYWRIGHT=1` 才执行，现有共享浏览器 smoke 没有开启该专项。已有 HTTP/gRPC 集成与通用 smoke 继续复用。

推荐顺序：**S1 运行基线 → S2 本人/公开关键链路 → S3 IAM 专项门禁**。E1 的只读灰度核对可穿插在 S1；E2 与产品体验扩展须满足各自条件。本阶段不预定发布版本，按实际变更及兼容性决定 PATCH/MINOR。

### S1 的证据范围

优先读取现有流量与现有账务记录：固定且已结束的时间窗口内，将 reservation、消费 ledger、log、来源用量事件及可见订阅进度关联；观察结算待办、对账差异、支付 pending 的年龄和后台最近结果。没有相应业务样本时明确写“未覆盖”，不为凑样本创建支付或付费模型请求。

普通只读核对不包含修改权限、停容器、重放支付、发送邮件或注入生产故障。若发现可重复异常，另起最小修复工作包，遵循仓库 diagnosing-bugs 技能，保留红色反馈与恢复证据。

### S2 的最小矩阵

| 身份 / 场景 | 重点断言 |
| --- | --- |
| 普通用户真实会话 | 本人首页、账本、按日统计、订阅进度有正确数据；伪造其他 user_id、失效或撤销会话被拒绝 |
| API Key | `/v1/subscription/usage` 绑定 Key 主体；无订阅与无效 Key 语义正确，无关服务 caller 被拒绝 |
| root / 财务只读 / 范围受限用户 | 余额零值、已用金额、隐藏财务与联系字段分别正确；只读用户看详情但不能提交写入；列表总数与行范围一致 |
| 匿名价格目录 | 仅公开且启用模型，分页/总数在过滤后计算，模态准确；目录依赖失败不泄露未过滤配置 |
| 桌面 / 手机 IAM 页面 | 长列表“详情”在视口内打开，关闭/切换记录与获准引用可用；409 必须重新加载/预检，禁止自动重试授权写入 |

### S3 的实施限制

- 固定契约检查复用 `cmd/rbac-contract-check`；新增入口应同时更新固定 caller grant、owner 分类、契约和正反例，包含 root 也不能隐式获得未来 operation。
- 浏览器复用 `internal/integration/iam_c_browser_test.go`、`web/playwright.rbac.config.ts` 和 `web/e2e/rbac-permissions.spec.ts`。现配置依赖 Chrome、Go 工具链、生成协议和 web 依赖，CI 应显式准备；若调整浏览器通道，需验证同一矩阵，不新造授权 mock。
- IAM/身份/owner/前端授权相关 PR 触发专项；共享 harness、工具版本和工作流自身的修改也应触发。全量三库 race 优先复用已有 fixture，按变更范围执行；涉及迁移/事务/并发时补齐对应三库证据，不把所有昂贵测试无差别塞入快速门禁。
- 检查所有 opt-in 环境条件，输出实际 executed/skipped 情况；CI green 不自动等于独立三库 IAM 或七组浏览器全部通过。

预计 S1 约半个工作日，S2 约 1–2 个工作日，S3 约 1–2 个工作日；这是规划估算，发现缺陷或浏览器环境问题后调整。先完成 S1/S2 盘点，再确定实际需要新增的测试数量。
