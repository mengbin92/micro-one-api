## 1. 当前事实与阶段边界

v0.23.2 已完成正式发布和 Responses / Anthropic 兼容修复部署，当前发布基线为
v0.23.2。executor 观察期间曾因回滚、修复 canary 和 allowlist 缩减多次重置；最新的
有效起点、样本限制与每日结论统一记录在
[`v0.23-executor-observation.md`](./v0.23-executor-observation.md)。
[`v0.22-post-release-observation.md`](./v0.22-post-release-observation.md) 的最终结论为
PASS：未发现可归因于 v0.22.x 的新增生产回归；观察期间发现的缺陷已通过
v0.22.1–v0.22.5 分别修复并发布。当前不因观察结论另开 patch 分支，后续 CI、文档和
executor 脚手架工作继续进入 develop。

v0.22 已接受 [Relay 执行边界 ADR](./v0.22-relay-execution-boundary-adr.md)：
server 保留 HTTP / SSE / WebSocket / gRPC 传输职责，executor 复用
`Plan → Reserve → Forward → Commit / Release → Log` 生命周期。v0.23 只实施
Chat Completions、Responses 和 Anthropic Messages 的 HTTP / SSE 首切片，旧路径在完整
观察窗口结束前保留；Responses WebSocket 本阶段只观察、不迁移。

当前仓库已经有一套早期 orchestrator 脚手架，实施应在其上做差距收敛，而不是重新
创建平行执行器：

- `internal/server/orchestrator.go` 已实现 Plan、Reserve、Forward、Commit / Release、Log
  生命周期，并同时支持流式与非流式结果；
- `internal/server/routes.go` 由 `relayOrchestrator.enabled` 加 token HMAC-SHA256 allowlist
  控制 `/v1/chat/completions`、`/v1/responses` 和 `/v1/messages`；命中 allowlist 的
  HTTP / SSE 请求进入 executor，未命中请求回到旧 handler；开关默认关闭；
- `internal/conf/relay_conf.proto` 已提供 `allowlist_token_hmac_sha256`，摘要以
  `SERVICE_TOKEN` 为密钥，原始 token 不进入配置；剩余差距是其余传输的
  transport-neutral 端口收敛；
- `internal/server/http_orchestrator.go` 仍在 server 层组装 billing / log hooks；staging
  路径优先使用 adaptor registry，未注册类型保留 `ProviderFactory` 兼容 fallback；
- executor 通过 `[]byte`、header map 和 `RelayStream` 暴露 transport-neutral 边界，HTTP
  状态、SSE flush 和连接关闭仍由 server 层负责。

本阶段明确不包含：

- Responses WebSocket executor 迁移（继续走旧路径并记录 `stream=true`）；
- `relay-gateway` 迁入 `app/relay`；
- 全量拆分 admin / identity 热点文件；
- 为消除重复而批量新建公共工具包；
- 未满足指标触发条件的多副本状态、分区、HPA / PDB 等议题。

## 2. P0 — v0.22.x 上线观察与 patch 决策

### 2.1 观察窗口（已完成）

从 2026-08-20 的初始快照起持续观察 48–72 小时。至少记录：

- 九个服务的容器状态、重启次数和最近错误日志；
- relay 请求成功率、5xx、P95 / P99、内存和 goroutine 趋势；
- 413 命中量及 endpoint 分布，确认 8 MiB JSON 限额没有误伤正常请求；
- channel 凭证解密失败、密钥/DSN/JWT fail-fast 和 Redis 降级告警；
- billing reservation 的 Commit / Release、重复结算、卡单和对账结果；
- 前端 RouteErrorFallback、通知查询失败和用户侧错误反馈。

初始与最终结论记录在
[`v0.22-post-release-observation.md`](./v0.22-post-release-observation.md)。最终结论为
PASS，已满足进入 executor staging 准备工作的前置条件。

### 2.2 v0.22.1 触发条件（历史决策，已收口）

满足任一条件才建立 v0.22.1 修复分支：

- v0.22.0 引入可复现的生产功能回归或 API / 配置兼容问题；
- 凭证迁移、加密写入或启动校验存在安全缺陷；
- 请求体限额对合法流量产生明确误伤，或超限路径仍导致内存风险；
- 计费出现重复 Commit、Release 遗漏、余额错误或无法自动恢复的卡单；
- 需要立即发布的依赖安全漏洞。

CI、文档、测试稳定性或下一阶段脚手架默认进入 develop，不单独消耗 patch 版本。

2026-08-20 已插入两个计划外生产缺陷修复，但不触发 v0.22.1：

- `938c6a4 fix: respect configured model sources`：修复订阅模型探测误监听通用
  channel 事件、手动配置模型列表被平台候选扩展，以及 account/channel 事件混淆；
- `ed6917e fix: harden responses protocol fallback`：修复 fallback 真实错误被掩盖、
  协议能力不匹配无法跨候选重试，以及请求级 4xx 误推进熔断器。

决策：两个提交保留在 develop，随下一个正式版本发布。`938c6a4` 包含兼容性
新增字段 `suppliers`，因此不适合拆成纯 patch；不把这两个提交计入 v0.23 executor
首切片完成边界，也不因它们提前或推迟 v0.22 观察结论。

## 3. P1 — 活跃 HTTP / SSE executor 首切片

### 3.1 端口与依赖方向

- 在业务执行层定义 `Executor`、`Planner`、`QuotaPort`、`Forwarder`、`StreamForwarder` 和
  `EventLogger`，接口不得引用 `http.Request`、`http.ResponseWriter`、SSE 或
  WebSocket 类型；
- server 负责鉴权头解析、请求体限额、DTO 转换、HTTP 状态和响应写回；
- 现有 `RelayUsecase.Plan`、quota helper、ProviderFactory / adaptor 和日志客户端
  通过小型 adapter 接入，不在首切片改变计费语义或存储模型；
- 新路径只通过 adaptor registry 分发，旧路径保持现状，避免单次请求同时跨两套
  分发决策。

### 3.2 首切片范围

接入以下精确入口的 HTTP 请求，包括实际主流的 SSE 流式请求：

- `POST /v1/chat/completions`；
- `POST /v1/responses`；
- `POST /v1/messages`。

1. feature flag 默认 `false`；
2. 仅 SHA-256 token allowlist 命中的测试账号或内部 caller 可进入新路径；Bearer 与
   Anthropic `x-api-key` 使用同一摘要 allowlist；
3. 未命中 allowlist、flag 关闭或新路径触发回滚时继续使用旧 handler；
4. `/v1/responses` WebSocket、资源子路径和无 model 的 stateful continuation 继续走旧路径；
5. 同一请求只能由新旧路径之一执行，禁止 shadow 请求触发真实重复扣费。

### 3.3 等价与失败测试

使用固定 fake ports 对新旧路径做 golden 对比，至少覆盖：

- 成功响应的状态码、允许透传的 headers、body、usage 和模型名；
- 上游 4xx / 5xx、超时、无候选和 quota reserve 失败的错误映射；
- failover 中失败候选 Release、成功候选 Commit，且只发生一次最终结算；
- context cancel、日志写入失败和健康回写失败不产生重复扣费；
- SSE 只有在协议终止事件完整到达后 Commit；截断、下游断开或错误终止事件必须 Release；
- flag / allowlist 关闭时完全回到旧路径。

### 3.4 2026-08-24 进展

- 新旧 `/v1/chat/completions` 非流式成功路径已加入 golden 对照：状态码、规范化响应体、
  Content-Type、Commit / Release 次数、usage 和日志关键字段保持一致。
- 新路径上游错误已统一使用 client-safe 错误映射；上游错误体不会原样返回，失败请求
  会 Release 且不写成功用量日志。
- API-key failover 已接入现有 `RetryExecutor`：固定 fake channel 验证即使失败候选 Release
  暂时不可用，重试仍使用独立幂等键，且成功候选只 Commit / Log 一次。
- transport-neutral 端口已在 `internal/biz` 定义，并由非流式 staging HTTP 路径通过
  server adapter 实际使用；已注册的 API-key / subscription channel 统一经过 adaptor
  registry，订阅凭据在转发前通过 resolver 解析。
- 失败矩阵已补齐：quota reserve 失败、context cancel、无候选、commit 失败、健康回写失败、
  日志写入失败均验证不会产生重复上游请求或重复计费；失败候选 Release 和成功候选单次
  Commit / Log 由既有 failover 测试覆盖。
- staging 门禁已验证默认关闭、仅 bearer-token SHA-256 allowlist 放行，清空 allowlist 即可
  回滚；E2E 脚本在缺失测试密钥时使用测试专用回退值，不修改部署配置。当前本机 Docker
  daemon 可用，但 compose 并行构建服务镜像时因 Docker Desktop 内存不足退出，
  `make test-e2e-suite` 仍需在提高构建内存或 CI 环境中重跑，未将该环境阻断误判为代码通过。
- `/v1/chat/completions`、`/v1/responses` 和 `/v1/messages` 的 SSE 请求已接入同一 executor
  生命周期；流结束后解析 usage 并 Commit / Log，截断流 Release，失败候选 Release 后可切换
  到下一候选，成功候选只结算一次。
- 新旧路径均输出 endpoint、stream、execution_path、HTTP status、terminal result、duration、
  quota outcome 和 failover reason/result 指标；观察起点与 PromQL 固化在
  [`v0.23-executor-observation.md`](./v0.23-executor-observation.md)。代码就绪不等于 7 天窗口已完成，
  窗口从部署后首次 allowlisted 请求被指标确认时开始计时。

## 4. 灰度、指标与回滚

### 4.1 Staging

- 默认关闭，只对内部 allowlist 开启；
- 连续观察至少 7 天，记录 success、error、failover、latency、quota outcome；
- 与旧路径按同口径比较成功率、P95、5xx、计费差异和 failover 结果；
- 按 [`v0.23-executor-observation.md`](./v0.23-executor-observation.md) 的启动条件、固定查询和
  日检表留证；没有 orchestrator 请求的自然日不计入有效观察窗口；
- staging 期间不改变生产默认值。

### 4.2 回滚条件

出现任一情况立即关闭 flag：

- 新路径成功率低于旧路径或出现新的稳定性错误；
- 重复 Commit、Release 未完成、账本与 reservation 不一致；
- P95 相对旧路径或既有基线回归超过 20%；
- failover 错误率显著上升或错误映射不兼容；
- executor 绕过 adaptor registry 或 transport 边界泄漏到业务层。

### 4.3 Production

只有 staging 连续观察达标后，才按租户或显式 allowlist 启动小流量 production
灰度。默认开启、旧路径删除和 WebSocket 迁移均不属于首切片 PR，必须分别满足 ADR
规定的观察周期并独立评审。

## 5. 质量门槛

普通变更：

```bash
make verify
```

Executor HTTP / SSE 切片追加：

```bash
go test -race ./internal/biz/... ./internal/server/...
make test-e2e-suite
cd web && npx playwright test
```

合并前必须证明：flag 默认关闭、新旧 golden 等价、quota 生命周期断言通过、回滚
只需修改运行时开关且不依赖数据库回滚。当前代码级门槛已通过；compose E2E 仍需在具备
足够构建内存的环境中通过后，才可启动 staging 观察窗口。

## 6. 触发式事项

| 事项 | 触发条件 |
|------|----------|
| 登录限流迁 Redis | identity 多副本已上线且观察到限流放大或容量计划明确要求 |
| selector 状态跨副本共享 | 多副本路由统计失真达到可观测阈值 |
| 订阅 fail-open 调整 | 已具备错误率、告警、收入风险证据和业务降级决策 |
| admin / identity 热点拆分 | 对应子域再次发生实质业务修改；一次只拆一个域 |
| 公共 ptr / pagination / strings 包 | 当前任务同时触碰至少两处重复实现且能减少 API 面 |
| Dockerfile / Compose 收敛 | 工具链或基础镜像升级需要同时修改多份文件 |
| relay 目录迁移 | executor 默认开启且遗留路径已删除 |
| 分区 / HPA / PDB / migration down | 延续既有容量与运维触发条件 |
