v0.21 阶段执行期间继续发布了兼容性 PATCH：[v0.20.1](../releases/release-v0.20.1.md)（前端依赖安全修复）、[v0.20.2](../releases/release-v0.20.2.md)（上游成本管理 + claim 覆盖守护）、[v0.20.3](../releases/release-v0.20.3.md)（迁移 smoke 与 nightly 稳定性）、[v0.20.4](../releases/release-v0.20.4.md)（路由死端熔断修复与分区安全守卫）和 [v0.20.5](../releases/release-v0.20.5.md)（Responses fallback 修复与 Release E2E 门禁）。`v0.21.0` 的阶段完成定义现已满足，本文进入发布收尾状态。

## 2. P0 — 事件驱动的资金安全验证

### 2.1 v0.20 迁移后首个结算周期对账（事件驱动，不随版本顺延）

**触发条件**：v0.20.0 上线后的第一个完整结算周期结束。

**原因**：迁移 `078` 改变了资金幂等闸门语义——`billing_ledgers` 上的全局唯一索引在分区方案下被移除，幂等由非分区 `billing_ledger_dedupe_claims` 表的主键在同一事务内仲裁。该语义必须有真实结算数据验证，不能只依赖单测。

**验收**：

- 结算周期内无未解释的重复 `ledger_dedupe_key` 账本；✅（0 重复；19 条迁移窗口孤儿已归因，唯一索引兜底）
- claim 冲突统一映射 `ErrLedgerDedupeExists` → `ErrDuplicateRequest`（HTTP 409），无驱动错误泄漏；✅（代码 + 单测链路验证）
- 对账脚本输出通过，异常项有闭环记录；✅（billing 全量对账 account 3 / channel 5 / receivable 1 为历史口径遗留；DB 侧检查全 PASS，毛利 24h +720,759 / 7d +7,362,712）
- 复核对账 / 告警阈值是否需要随新幂等语义调整。✅（无需调整；建议新增 claim 覆盖完整性检查入 DB 侧）

## 3. P1 — 质量门禁补齐

### 3.1 MySQL/Postgres migration smoke（可拆 PATCH）

- 目标：在 CI 中用 MySQL / PostgreSQL service-container 真实执行 fresh + incremental 迁移，补齐 SQLite 已自动化之外的两方言运行时验证；
- 现状：`make migration-check` 覆盖三方言静态镜像、ownership 与重复前缀，但不执行 SQL；Postgres / SQLite README 中“CI 已运行 scratch database”的表述超前于实际 CI，需随本项一并修正；
- 实施切分：第一阶段先落地 **fresh + repeat 幂等 + 状态审计**；incremental 先覆盖 consolidated baseline 之后的最近增量镜像，不强求补齐全部历史升级链路；
- 验收：CI 失败注入能捕获方言语法 / 约束问题，迁移日志与 `schema_migrations` 状态可审计；锁等待场景待后续真实 DDL 需要时再扩展。

### 3.2 release 挂钩 admin e2e（先准入，后提升）

- 前置条件：nightly compose E2E + Playwright admin smoke 在 v0.20.0 修复后连续稳定（建议连续 5 次或稳定 1–2 周）；✅（2026-08-17 最终修复后连续 5 次成功，最后为 scheduled run `31989324792`）
- 当前状态：✅ `nightly.yml` 改为调用 reusable `e2e.yml`（compose E2E + Playwright admin smoke 单一事实源）；`release.yml` 通过 `release-context` 解析目标 tag，并把 E2E 设为 Docker 构建 / 推送与 GitHub Release 的前置依赖。E2E 失败时镜像和 Release 均不会发布。
- 远端调用验证：✅ 2026-08-18 在 `ci/release-e2e-gate@be8e46e` 手动触发 Nightly E2E（run `32087512854`），`e2e / Compose E2E suite` 与 `e2e / Playwright admin smoke` 双 suite 成功，证明 reusable workflow 在远端可调用且语义正常。
- 真实发布验证：✅ `v0.20.5` Release run `32110577994` 已确认 tag 基线上 E2E 先行、Docker 多架构镜像与 GitHub Release 全部成功；失败工件上传能力保留。
- 验收：✅ release tag 工作流在镜像发布前执行 e2e，失败即阻断发布；已完成至少一次真实发布验证。

- 当前 dedupe claim 冲突 / 回滚没有应用级 Prometheus counter；为避免仅为观察而改动资金热路径，首季使用 DB 行数增长与 claim ↔ ledger 双向覆盖作为代理口径，并在模板中登记指标缺口；
- 输出进入后续 P3 议题准入评估，不直接触发实现。

### 4.2 手动分区 DDL 预演（触发式）

- 阈值：生产 ledger / logs 表接近 1GB 或 1000 万行前，完成一次生产等价演练；
- **硬性顺序**：ledger 分区脚本执行前必须已应用迁移 `078`，且 `billing_ledger_dedupe_claims` 存在并完成存量回填；
- ✅（2026-08-15）`migrations/manual/phase3_*.sql` 已内置前置守卫：ledger 脚本会校验 `schema_migrations`、迁移 `078` 已应用且 ledger → claim 覆盖为 0 缺失；logs 脚本会校验目标 schema 已纳入 `schema_migrations` 治理。任一条件不满足即 `SIGNAL` 中止，后续 DDL 不会执行。守卫已用 MySQL 8.0 scratch 容器验证通过/阻断路径；
- 验收：演练记录包含备份、执行时长、锁影响、回滚方案与分区校验结果。

### 4.3 热点文件拆分（触发式）

- 触发条件不变：admin http / channel data / billing biz / relay biz 仅在对应文件因业务需求再次修改时拆分；
- 禁止为了拆分而拆分，禁止同一 PR 混拆多个热点。
