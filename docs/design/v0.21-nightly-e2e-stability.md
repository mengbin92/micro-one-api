## 1. 当前结论

- **scheduled main 的两次失败不是 flaky，而是 nightly 监测点停留在旧基线。**
  - `main@6b10de1` 是 `v0.19.1` 发布合并提交；
  - 当晚 scheduled run `31768353982` 实际运行的也是该提交；
  - E2E 修复（`5ebe403` / `485b0da`）和 v0.20 系列后续修复都已在 `develop`，但尚未进入当晚的 `main`。
- **develop 的失败 → 成功序列符合“修复后收敛”**：
  - 02:02 `e074068` 失败；
  - 02:44 `20e1216` 失败；
  - 03:20 `3b36c36` 成功。
- **Compose 失败的直接原因**：旧 compose 中 Prometheus/Grafana 绝对路径 bind mount 在 CI 不存在；Docker 自动创建目录导致“file onto directory”挂载错误。
- **Playwright 失败的直接原因**：旧 spec 仍断言英文文案与旧组件结构；前端已中文化并重构，spec 在 `5ebe403` 才同步修复。
- **附带发现**：MySQL healthcheck 使用 `localhost` 时可能命中 entrypoint 的临时 Unix socket，在 TCP 3306 尚未可用时提前 healthy。本次已改为强制 `127.0.0.1` TCP readiness，降低 migrate one-shot 的启动竞态。
