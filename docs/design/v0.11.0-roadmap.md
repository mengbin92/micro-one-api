# v0.11.0 下一阶段工作路线图

> 状态：建议稿，作为下一阶段执行入口
>
> 基线：`develop@89ed1b9`（v0.10.2，2026-07-27）
>
> 主题：计费准确性、模型数据治理与路由运营闭环

## 1. 结论摘要

下一阶段不再继续扩张架构重构范围，建议以 **v0.11.0** 为目标，按以下顺序推进：

1. **P0：统一 token 语义并补齐 `cache_creation` 全链路**。先解决已知的用量丢失和潜在成本低估，再增加新运营能力。
2. **P0：治理模型规范 ID 与价格数据**。清理仅大小写不同的重复模型，阻止重复数据再次进入系统，并补齐上游成本配置。
3. **P1：增加统一路由和计费可观测性**。让普通渠道与订阅账号的实际流量分布、回退、未定价和成本偏差可查询、可告警。
4. **P2：完成模型导入导出**。现有批量启用、禁用、删除已经落地，本阶段只补批量配置迁移能力，不重复建设批量状态操作。

建议发布策略是 **先采集、后核对、再收费**：`cache_creation` 字段和统计先以观察模式上线，确认生产样本与供应商账单一致后，再显式开启新价格桶。禁止在字段上线时静默改变既有用户扣费。

## 3. 范围与成功标准

### 3.1 本阶段目标

- 支持 OpenAI-compatible、Anthropic Messages 和转换后的 Chat Completions 路径使用同一套、不重叠的计费 token 桶。
- 日志、账本、聚合 API 和管理端能够展示缓存创建量，并能按 5 分钟/1 小时 TTL 分别配置价格。
- 公开模型 ID 在 biz 与数据库两层都满足 `trim + lowercase` 规范，上游大小写和供应商前缀只存入 `upstream_model_id`。
- 用户售价和上游采购成本分离；普通渠道和订阅账号均有无歧义的成本键。
- 运营人员能回答：请求选中了哪类上游、是否回退、哪些活跃模型未定价、缓存价格是否造成毛利异常。
- 模型配置可通过版本化文件 dry-run、导入和导出，失败时不留下部分数据。

### 3.2 非目标

- 不重做已完成的 `BatchModels`。
- 不在本阶段引入新的微服务、消息中间件或计费数据库。
- 不重新启动 grpc-gateway 迁移，不降级 log-service；当前 log-service 承担持久化、查询和聚合职责，不满足组件化前提。
- 不以“支持更多国内平台”为独立大任务。新增平台必须由真实需求驱动，并复用 provider conformance fixture；不能为平台复制一条专用账务链。
- 不删除旧 proto 字段或旧数据库列；本阶段数据库变更保持 additive，兼容滚动升级与回滚。

## 4. 执行计划

### Phase 0：token 语义设计门（P0，1-2 人日）

先形成一页 ADR 并固定测试向量，再修改 proto。规范内部计费桶：

| 规范桶 | 含义 |
|--------|------|
| `uncached_input_tokens` | 不属于缓存读取或缓存创建的输入 token |
| `cache_read_tokens` | 从 prompt cache 读取的 token |
| `cache_creation_5m_tokens` | 写入 5 分钟 TTL cache 的 token |
| `cache_creation_1h_tokens` | 写入 1 小时 TTL cache 的 token |
| `output_tokens` | 输出 token |

兼容规则：

- `prompt_tokens` 保留现有 API/日志含义，不直接改名或删除；billing 使用规范桶计算，避免从一个兼容字段猜测供应商语义。
- OpenAI：cached tokens 是 prompt 子集，规范化为 `uncached = max(prompt - cached, 0)`。
- Anthropic：`input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens` 互不重叠，规范化时不得相减。
- 若供应商只返回 `cache_creation_input_tokens` 总量而无 TTL 明细，写入 `cache_creation_5m_tokens` 还是单独 `cache_creation_tokens` 必须在 ADR 中固定；不得依据模型名猜测。
- 非法负数归零；TTL 明细之和大于总量时记录解析异常指标，不用不一致数据改变扣费。

交付物：

- `docs/design/token-usage-semantics.md`。
- provider/relay/billing 共用的表驱动 fixture，至少覆盖 OpenAI cached、Anthropic 5m、Anthropic 1h、总量无明细、流式首尾 usage 合并和异常值。

验收：同一 fixture 经 raw relay、provider 转换和 billing 后得到相同的五桶结果；评审通过前不进入 Phase 1。

### Phase 1：`cache_creation` 采集、存储与计费（P0，5-7 人日）

#### 1.1 解析与领域传递

- `internal/server/http_raw_helpers.go`：解析 `cache_creation_input_tokens` 与 `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`。
- `domain/upstream/provider/`：扩展 usage DO；非流式和 SSE 流式路径采用相同合并规则。
- `internal/server/http_usage_log.go`：把规范桶传给 log 与 billing，不在 service 层实现价格规则。
- 为未知字段、缺少 TTL 明细和不一致总量增加低基数 metrics；结构化日志可记录模型和上游 ID，Prometheus label 不使用 channel/account ID。

#### 1.2 DTO、DO、PO 与数据库

- 扩展 `api/log/v1/log.proto`、`api/billing/v1/billing.proto` 及必要的 common DTO，运行 `make api`，不手改生成文件。
- 扩展 log/billing 的 DO、PO、转换函数、写入、查询和聚合；service 仅做 DTO 与 DO 转换。
- 新增下一可用编号的 MySQL 迁移，并同步 PostgreSQL/SQLite 完整 schema 与增量迁移。
- `logs`、`billing_ledgers` 至少持久化 5m/1h 两个创建桶；是否额外保存总量由 ADR 决定，禁止总量与明细在聚合时重复求和。
- 更新 `migrations/ownership.yaml` 和 schema split 清单。

#### 1.3 价格与扣费

- `ModelPrice` / `UpstreamModelPrice` 增加可选的 `cache_creation_5m_price`、`cache_creation_1h_price`。
- 未配置创建价格时保持 v0.10.2 扣费行为，并标记为“未定价”，不默认套用 input price。
- 增加观察开关，例如 `BILLING_CACHE_CREATION_MODE=observe|charge`，默认 `observe`；观察模式写 token 与影子成本，但不改变用户余额。
- 用户费用、上游成本、订阅用量和 reconciliation 使用同一个纯计算函数，避免四处复制价格公式。
- 管理端价格页展示创建价格、未定价状态和观察/收费模式；日志页、用量页、dashboard 展示创建 token，但不把多个桶重复计入总 token。

#### 1.4 发布与验收

- 单测：解析、SSE 合并、DTO/DO/PO 转换、价格缺省、5m/1h 计价、负数/溢出和聚合。
- 存储测试：MySQL 主路径，加 PostgreSQL/SQLite smoke test；旧行新增列默认 0。
- 集成测试：一次 Anthropic 非流式和一次流式请求，从上游 usage 一直核对到日志与 ledger。
- 生产先运行 `observe` 至少一个完整结算周期，对比供应商账单；偏差在约定阈值内且无重复计数后才切 `charge`。
- 回滚只需切回 `observe`；新增列保留，不执行破坏性 down migration。

### Phase 2：模型规范 ID 与成本治理（P0，5-7 人日）

#### 2.1 规范 ID 收敛

- 在 channel biz 定义唯一入口 `CanonicalModelID = strings.ToLower(strings.TrimSpace(id))`；create、update、alias、自动发现和导入均调用该入口。
- 数据库增加大小写不敏感的规范唯一约束：MySQL、PostgreSQL、SQLite 分别使用适合驱动的实现，不依赖单一方言 SQL。
- 迁移前先提供只读 preflight 报告，列出重复模型及其 aliases、channel mappings、subscription mappings、usage stats 和价格引用。
- 合并迁移必须在事务中重指向所有外键/统计后再删除重复行；发现冲突时终止并输出报告，不做 `INSERT IGNORE` 式静默覆盖。
- 保留精确上游名称到 `upstream_model_id`，公开 `model_id` 不承载供应商前缀或大小写需求。

#### 2.2 用户售价与上游成本分离

- 固定成本键命名，建议使用 `channel:<id>:<upstream_model_id>` 与 `subscription:<id>:<upstream_model_id>`；提供旧 `<channel_id>:<model>` 键的兼容读取和迁移工具。
- 增加独立上游成本管理视图，按来源类型、来源名称、精确上游模型 ID 配置，不把采购成本写入公开模型售价。
- 价格保存前显示“已路由但未定价”模型数；未定价不阻断保存，但必须有醒目状态、审计事件和指标。
- 增加同一公开模型分别命中普通渠道、订阅账号和另一供应商时的回归测试：用户售价一致，上游成本按来源分别记录。

验收：

- 数据库中不存在 `LOWER(TRIM(model_id))` 重复；通过 API 再创建大小写变体返回明确的 typed error。
- `/v1/models`、日志 `model_name`、`ModelPrice` 键全部使用规范公开 ID，`upstream_model_id` 保持原始精确值。
- 活跃路由的未定价清单可查询，用户收入、上游成本和毛利可在同一请求/ledger 上核对。

### Phase 3：统一路由可观测性（P1，3-5 人日）

- 先收敛选择器语义：`priority` 只用于分层，新增明确的订阅账号 `weight` 并贯穿 DTO/DO/PO；跨来源选择不得继续把订阅账号权重硬编码为 1。
- 对 `Acquire/Release` 做明确取舍：接入真实的请求生命周期反馈，或删除/停用对空载荷信号的依赖并修正文档；不能继续宣称尚未生效的 load-aware 能力。若跨服务反馈会增加热路径 RPC，优先使用现有 Redis 并发状态或异步 best-effort 反馈，并用故障测试证明失联时退化安全。
- 增加 2 个普通渠道 + 2 个订阅账号的确定性分布测试，覆盖不同优先级、权重、健康降权、并发饱和和来源失败，先证明选择行为再制作运营视图。
- 在选择与执行边界分别记录：候选来源、最终来源、粘性命中、优先级层、回退原因、执行结果和耗时。
- Prometheus 指标只使用 `source_kind`、`result`、`reason`、`provider_family` 等受控 label；channel/account/model 明细放结构化日志或 trace，避免高基数。
- 增加管理端运营视图：普通渠道/订阅账号流量占比、回退率、错误率、缓存读写 token、用户收入、上游成本和毛利。
- 为以下情况增加告警：有流量但用户售价缺失、上游成本缺失、观察成本持续偏离供应商账单、单一来源流量长期偏离配置权重、cache usage 解析异常。
- 更新 `docs/design/BASELINE.md` 或新增 v0.11 基线，记录改造前后 relay P95/P99 与 billing 提交耗时，确认新增统计未使热路径明显回退。

验收：使用固定权重压测时，实际来源分布在样本容差内；强制一个来源失败后，dashboard 和 metrics 能显示回退原因且账单只落一次。

### Phase 4：模型导入导出（P2，4-6 人日）

- 定义版本化 JSON schema，覆盖模型、别名、渠道映射、订阅映射；价格默认不随模型导出，除非显式选择并通过独立权限校验。
- 导入支持 `dry_run`，返回新增、更新、跳过、冲突和错误明细；正式导入采用事务，任一非法记录导致整批回滚。
- 明确冲突策略为 `reject` 或 `update`，默认 `reject`；不得根据记录顺序隐式覆盖。
- 设置文件大小和记录数上限，校验 canonical model ID、外键目标、重复 alias、权限和敏感字段；导出不得包含渠道 API key、OAuth token 等密钥。
- 管理端提供下载、上传、dry-run 结果确认和失败报告；复用现有列表筛选与选择状态，不再新增第二套批量状态 API。
- 写入审计事件，至少记录操作者、request ID、schema 版本、记录数、摘要 hash 和结果。当前通用 audit middleware 的 actor/request ID 提取仍是空实现，导入 API 必须先接入认证上下文或显式传入 actor，禁止落空操作者审计记录。

验收：同版本空库 round-trip 后模型及映射等价；含冲突或非法外键的文件不会产生部分写入；导出内容安全扫描不含凭据字段。

## 7. 发布、回滚与完成定义

### 7.1 发布顺序

1. 备份 billing/log/channel schema，运行 migration status 和模型重复 preflight。
2. 先发布兼容新字段但仍为 `observe` 的 billing/log/relay，再发布管理端。
3. 观察至少一个完整结算周期，核对 token 桶、影子成本、供应商账单和 ledger 去重键。
4. 完成 canonical model 数据合并后再启用数据库唯一约束。
5. 录入并复核价格后，按小流量到全量切换 `charge`；每次切换保留可逆配置。
6. 最后开放导入入口，初期仅管理员角色可见。

### 7.2 回滚策略

- 计费异常：立即切回 `observe`，不回滚新增列；根据 ledger dedupe key 生成冲正，不直接改余额。
- 路由观测异常：关闭新 dashboard/指标采集，不改变选择器行为。
- 模型规范化失败：唯一约束前可回滚应用；数据合并前保留映射报告和备份，禁止无备份执行清理。
- 导入异常：关闭入口；事务回滚保证无需逐行修复。

### 7.3 v0.11.0 完成定义

## 8. 暂缓清单与重新评估条件

| 暂缓项 | 重新评估条件 |
|--------|--------------|
| 新增更多 provider 专用实现 | 有真实调用需求、协议差异无法由 OpenAI-compatible/Anthropic adaptor 表达，并有可脱敏 fixture |

| 更大范围架构重构 | v0.11 基线显示当前架构无法满足明确 SLO，而不是仅因目录或代码风格偏好 |
