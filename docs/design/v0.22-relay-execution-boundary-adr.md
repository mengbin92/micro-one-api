# v0.22 Relay 执行边界 ADR

- 状态：已接受，首个切片待独立 PR
- 日期：2026-08-19
- 范围：`relay-gateway` 的 Chat Completions 入口

## 1. 决策摘要

保留 `internal/server` 作为 HTTP / gRPC / SSE / WebSocket 的传输边界，新增
transport-neutral 的 relay executor 作为业务执行编排边界。首个切片只迁移
Chat Completions 的非流式 HTTP 路径；旧 handler 保留并由 feature flag 控制，
观察窗口结束前不删除遗留路径，也不搬迁整个 `internal/server` 目录。

执行顺序固定为：`Plan → Reserve → Forward → Commit`，失败或取消执行
`Release`，最后写入 `Log`。executor 只返回结构化结果和生命周期事件，不直接
写 `http.ResponseWriter`，因此同一套执行逻辑可被 HTTP / gRPC 适配器复用。

## 2. 边界与接口

### 2.1 Executor 输入 / 输出

```go
type ExecuteRequest struct {
    Token     string
    Model     string
    Endpoint  string
    Body      []byte
    Headers   map[string][]string
    RequestID string
    Stream    bool
}

type ExecuteResult struct {
    StatusCode  int
    Headers     map[string][]string
    Body        []byte
    Usage       Usage
    ChannelID   int64
    RequestID   string
}

type Executor interface {
    Execute(context.Context, ExecuteRequest) (ExecuteResult, error)
}
```

`Body` 由 server 负责读取和限额，executor 不接受 `http.Request`、不返回
`http.ResponseWriter`，也不依赖 SSE / WebSocket 类型。`Headers` 只携带转发所需
的白名单字段，禁止让 executor 接管连接升级、压缩和跨域响应。

### 2.2 生命周期端口

executor 依赖以下 transport-neutral 端口：

- `Planner`：鉴权、模型解析、渠道选择和 failover 候选；
- `QuotaPort`：`Reserve`、`Commit`、`Release`；
- `Forwarder`：接收规范化请求并返回上游响应或流；
- `EventLogger`：记录 request、route、quota 和 error 事件。

现有 `RelayUsecase.Plan`、`reserveQuota` / `commitQuota` / `releaseQuota`、
`ProviderFactory` 和日志客户端作为首个实现的适配器，不在该 PR 中改变账务
语义或存储模型。

## 3. 传输层职责

- HTTP：读取并限制 body、解析鉴权头、写状态码和普通响应；
- SSE：复制上游 headers、发送 `data:` 帧、处理 flush 和断开；
- WebSocket：处理 Upgrade、首帧超时、读写 deadline 和 graceful drain；
- gRPC：把 protobuf DTO 转成 `ExecuteRequest`，把 `ExecuteResult` 转回 DTO；
- executor：只处理 Plan / Reserve / Forward / Commit / Release / Log，不能
  直接访问 transport writer。

流式请求在 `Forward` 返回 stream handle 后由 server 负责消费；每个生命周期
事件必须携带同一个 `RequestID`，结算只在收到可确认 usage 或既有成功条件后
执行，断流走 Release / partial-log 的现有语义。

## 4. Adaptor registry 与 ProviderFactory

`AdaptorRegistry` 成为协议 / 渠道类型的唯一分发入口。registry 根据
`Endpoint + ChannelType + Protocol` 返回 adaptor；`ProviderFactory` 保留为
API-key 等传统渠道的底层 provider factory，由 registry 的默认 adaptor 调用。
OAuth / subscription adaptor 继续复用当前 hybrid adaptor，不把 factory 逻辑
复制到 server。

迁移期间禁止 server 同时直接选择 registry 和 factory：旧路径继续走现有
factory，新 executor 路径只依赖 registry port，这样可按入口切换并独立回滚。

## 5. Orchestrator flag 时间表

| 阶段 | 默认值 | 规则 |
|---|---:|---|
| staging 首切片 | `false` | 只对测试账号 / 明确 allowlist 开启，保留旧路径指标对照 |
| staging 稳定窗口 | `false` | 连续观察至少 7 天：成功率、P95、计费差异、failover、5xx |
| production 灰度 | `false` | 按租户或 header allowlist 逐步扩大，出现回滚条件立即关闭 |
| 默认开启 | `true` | 达到稳定窗口门槛后，旧路径仍保留一个发布周期 |
| 删除遗留路径 | — | 默认开启后再观察一个完整结算周期，独立 PR 删除并保留迁移说明 |

具体日期由发布负责人依据流量和指标确认；本 ADR 不授权在首切片中修改默认
值，也不把 orchestrator flag 的删除作为 v0.22 前置条件。

## 6. Chat Completions 首切片验收

- HTTP 非流式成功响应与旧路径逐字段等价（状态、headers、usage、模型名）；
- 上游 4xx / 5xx、超时、无候选、quota reserve 失败均保持既有错误映射；
- failover 候选只执行一次结算，失败候选 Release，成功候选 Commit；
- 请求级指标至少覆盖 success、error、failover、latency 和 quota outcome；
- 同一请求在旧 executor / 新 executor 下使用固定 fake ports 做 golden 对比；
- 灰度期间出现成功率下降、重复扣费、Release 未完成、P95 回归超过基线
  20% 或 failover 错误率显著上升时，关闭 flag 并回到旧 handler。

首切片不包含 SSE、WebSocket、Anthropic Messages、Responses 资源续接或
`relay-gateway` 目录迁移；这些项目必须在 executor 端口和观察指标稳定后单独
立项。
