## 2. 范围与成功标准

### 2.1 本阶段目标

- 并发相关的测试在 CI 中受 `-race` 守护,测试基础设施自身不再出现 data race。
- cache-creation charge 计费进入稳态:毛利/cache 价格异常可告警,对账可自动化执行。
- 发布门禁补完:强制失败验证有明确执行脚本与验收记录。
- 全仓库遗留 TODO 清零;BASELINE 基线有可对比数据。
- 性能热点(jsonx Marshal)有实测结论与明确的保留/优化决策。

### 2.2 非目标

- 不主动启动 P2.1(Claude 上游配额窗口同步)、P2.2(账号池有界等待)、#7 第二步——触发条件不满足。
- 不重启 grpc-gateway 迁移、log-service 组件化等已决策暂缓项(ADR 重开条件见 P3.3)。
- 不新增微服务、消息中间件或计费数据库。
- 数据库变更保持 additive,不删除旧字段/旧列。

### P1 — 运营闭环(charge 之后,约 2-3 人日)

1. **charge 后监控告警** ✅
   - 基于 `relay_token_usage_shadow_cost` / `billing_ledgers` 聚合,为以下场景增加 Prometheus 告警规则(或文档化查询):
     - cache-creation 计费桶毛利异常(负毛利、偏离供应商账单阈值);
     - 已路由但未定价模型(cache_creation 桶未配价)持续产生流量;
     - 观察成本与 charge 成本长期偏离(影子成本 vs 实扣)。
   - 管理端 `routing-ops` / 成本视图确认 charge 后展示正常。
   - 落地:新增 `micro_one_api_billing_ledger_gross_profit_quota` 指标与三条告警
     (`CacheCreationChargeUnpricedTraffic` / `CacheCreationChargeSignalLost` /
     `NegativeGrossMargin`);文档化 SQL 查询与验证步骤见监控 runbook;Grafana 新增
     3 个 charge 面板。
   - 📌 口径:毛利指标仅覆盖**成功 commit 写入 ledger 的请求**(release/失败/未写
     ledger 不记录),`NegativeGrossMargin` 反映的是已结算请求的毛利;结算失败缺口
     需结合 `BillingLedgerUpstreamCostRecorded{result="unpriced"}` 与对账输出排查
     (runbook「口径说明」)。
2. **对账周期自动化** ✅
   - 将 observe 阶段的手工核对脚本化为可重复执行的检查(ledger dedupe key、token 桶 vs 供应商账单、缓存命中率口径)。
   - 落点建议:`scripts/reconcile/` 下新增检查脚本 + 文档(README 说明用法与阈值)。
   - 验收:一次命令完成周期对账,输出差异报告;无差异时 exit 0。
   - 落地:`scripts/reconcile/reconcile.sh` + `scripts/reconcile/checks.go`
     (billing 全量对账触发、dedupe key、counted-but-unbilled、毛利、缓存命中率口径、
     供应商账单 CSV 对比),`README.md` 说明用法与阈值;无差异 exit 0。
   - ⏳ 跟进:默认阈值(`--vendor-tolerance 0.05`、`--unpriced-max 0`、告警 `>100`/`30m`)
     为首次假设值,需生产第 1 个结算周期观察模式校准后固化为生产基线(校准流程见
     `scripts/reconcile/README.md`「阈值校准」)。
3. **发布后强制失败验证(补完 §9.2)** ✅
   - 编写执行清单/脚本:强制一个普通渠道 + 一个订阅账号分别失败,确认:
     - dashboard/metrics 显示正确回退原因;
     - 最终 credential/usage/成本/账单只归属实际服务来源;
     - 账单只落一次(无重复扣费)。
   - 验收:验证步骤可复现,结论回写发布说明。
   - 落地:runbook(手工清单 + 等价 SQL)+ `scripts/verify-forced-failure.sh`
     (两场景自动禁用/回退/断言 metrics 与账本归属、单次计费)。

### P2 — 按需增强(触发条件驱动,不主动启动)

| 项 | 触发条件 | 来源 |
|----|----------|------|
| P2.1 Claude 上游配额窗口同步 | Claude 可调度账号 ≥2,存在可靠的结构化 usage/reset 信号,且本地 5h 估算与上游限流出现明显偏差 | p2-ops-enhancement-conclusion.md + 本次评审修订 |
| P2.2 账号池有界等待 | `subscription_failover_total{reason="concurrency",result="exhausted"}` 持续达到阈值并产生用户侧 503;预计等待时间低于请求剩余 deadline | 同上 |
| #7 Chat/Responses/WS 粘性语义统一 | 多账号 fan-out 与稳定 session key 同时存在,并观察到跨账号 rebind 或可量化的 prompt-cache 损失 | p1-contract-hardening-conclusion.md + 本次评审修订 |

触发口径说明:

- P2.1 已有本地 `quota_5h_limit_usd/used_usd/window_start` 作为保守预算;待办仅是
  **上游真实窗口同步**,不重复建设本地 5h 窗口。无可靠上游信号时继续使用本地窗口
  与 runtime blocker,不从不稳定 error message 推断计费窗口。
- P2.2 的饱和指标是 `micro_one_api_relay_subscription_failover_total{reason="concurrency"}`;
  `RelayAccountConcurrencyFallbackTotal` 仅表示 Redis limiter 故障降级,不得用于判断账号
  并发打满。先区分单实例 bounded wait 与多实例 distributed fair queue,不新增与现有
  limiter 重复的 per-account semaphore。
- #7 现有 Responses/WS scheduler、Redis sticky store 与 schedulability 校验已接线;后续
  工作聚焦 Chat/Responses/WS 的 hit/miss/rebind 观测和 failover 后 rebind 语义统一。
  启动前先补 session key 覆盖率口径,避免将“无 series”误判为“无收益”。

### P3 — 架构方向(中期议题,穿插推进)

1. **修复并刷新可复现的性能基线**
   - 先修 `scripts/benchmark/k6-baseline.js`:吞吐使用 `http_reqs.values.rate`,HTTP 500
     不得计为成功;显式配置 `summaryTrendStats` 与 endpoint tag 子指标。
   - 提供确定性的 mock upstream/fixture;明确 k6 只采集 HTTP 指标,gRPC 延迟、billing
     commit、routing selection、缓存命中率与熔断状态通过文档化 Prometheus 查询采集。
   - 在同一 Linux/amd64 环境、同一配置与数据集上运行准确的 Phase 0 Git SHA、
     `v0.16.0`(`a8e14db`)与执行时的 develop Git SHA,每个版本至少 3 次并归档原始结果。
   - 无法恢复的历史 Phase 1/2 数据标记为 `N/A — not recorded` 并说明原因,不以推测值
     消除 TBD。验收是当前基线可复现、原始数据可追溯、版本间可公平比较。
2. **jsonx Marshal/Encoder 性能决策**
   - 现状:Apple M5 Pro 微基准确认 sonic Unmarshal 快约 2.3x,但 Marshal 慢约 2.1x
     (约 318ns vs 150ns);该结果不直接代表生产 Linux/amd64。
   - 增加代表性 benchmark:小 request struct、Responses/Anthropic 大事件、admin/billing
     map+slice 响应及 `NewEncoder`;重点覆盖 `internal/apicompat` 与 adaptor 热路径,不只测
     admin-api/billing service。
   - 在固定 Linux/amd64 runner 上用多次 benchmark + CPU profile 判断请求级影响;只有
     JSON 编码占比或总体 CPU/吞吐/尾延迟出现可重复改善时,才评估 `Marshal` 单独回退
     std。`NewEncoder` 独立决策,不得假设切换 Marshal 会改善 Encoder 路径。
   - 决策落档到 `docs/design/` 或 `pkg/jsonx` 注释,保留现有 JSON 兼容测试作为门禁。
3. **ADR watchlist(不作为 v0.17 主动交付)**
   - log-service:当前仍拥有查询、持久化、批量删除/分区维护,且 relay/admin 存在远程
     调用。仅当独立部署/存储/RPC 成本明显高于隔离收益,并已有明确替代所有者时重开
     组件化/合并决策。
   - grpc-gateway:`docs/migration/grpc-gateway-migration-todo.md` 的“不引入 runtime”
     决策继续有效。仅当多个独立 gRPC backend 需要统一外部 REST facade、集中 auth/
     metadata/转码,且 Kratos 生成 HTTP handler 无法满足时重开 ADR。
