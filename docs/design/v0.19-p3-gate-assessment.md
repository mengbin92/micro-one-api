## 一、准入评估结论（五议一不触发，全部维持触发式）

| 议题 | 触发条件（文档定义） | 当前证据（2026-08-11/13 实测） | 判定 |
|---|---|---|---|
| 表分区 | 单表 ≥1 GB 或 ≥1000 万行；或规模相关慢查询；或按月清理需求 | `logs` 13 MB / ~22.9k 行；`billing_ledgers` 24 MB / ~22.7k 行（v0.18 C4 runbook 实测）；`billing_ledgers` 原唯一索引不含分区列；2026-08-13 已由迁移 078 的非分区 claim 主键和按 schema DDL 解决 1503/全局幂等前置 | ❌ 不触发，差 2 个数量级；机制已就绪（`platform/database/partition` + `partition.enabled` 开关） |
| 会话窗口统一 | sticky hit/miss/rebind 数据证明 prompt cache 或会话亲和收益显著 | 当前生产流量为**单账号**（zhipu/kimi）订阅，无 Claude Pro 多账号池（p2-ops P2.1 结论）；sticky 指标 `RelaySubscriptionStickyTotal{result=hit|rebind|miss|reused_unschedulable}` 已埋点，命中率可直接计算 | ❌ 不触发；前置条件（多账号池）不满足；**触发数据已可观测** |
| 负载感知排队 | 选路失败/瞬时并发导致的 502/429 达持续阈值，且简单 failover 无法解决 | 账号池未饱和（p2-ops P2.2 结论）；性能基线 Error Rate 0.12%（mock，多来自 mock 限流）；熔断 `circuit_breaker_state`=closed ×4 服务、trips=0；gRPC 四服务 P50/P95/P99 已有实测 | ❌ 不触发；但**触发指标存在缺口**（relay HTTP 入口无请求级状态码/延迟埋点，见 §二） |
| log-service 合并 | 独立部署/RPC/存储成本持续高于隔离收益，且替代 owner 清晰 | 独立 compose 服务（`app/log/Dockerfile`，独立 DB/Redis 访问）；仓库无成本/流量数据，无替代 owner 分析 | ❌ 不触发；需运营侧提供资源用量与调用成本数据 |
| grpc-gateway 迁移 | 多个独立 gRPC backend 需要统一外部 REST facade，Kratos 生成 HTTP 无法满足 | relay-gateway 是**唯一**对外 HTTP 入口（:8080）；identity/channel/log 为内部 HTTP 端点；Kratos 生成 HTTP 满足现状 | ❌ 不触发；外部 facade 单一，无多 backend 统一需求 |

**结论**：P3 五大议题均未达到立项阈值，继续维持触发式，不主动实施任何产品功能（符合规划文档 §9「不建议现在做的事」）。

## 二、触发条件可观测性缺口（P3-0，本次已实施）

「指标触发」的前提是指标存在且可查询。逐项核对后，唯一缺口在 **relay HTTP 入口**：

- 现状：relay-gateway 已有 `/metrics`（`metrics.Handler()`）与丰富的业务指标（sticky/failover/concurrency/熔断/gRPC client 延迟）；但 **HTTP server 入口没有请求级中间件埋点**——`micro_one_api_http_requests_total` / `micro_one_api_http_request_duration_seconds` 已注册但从未被任何服务接线（孤儿指标），无请求总数、状态码分布、请求延迟。
- 后果：负载感知排队的触发条件「**502/429 达到持续阈值**」无法用 PromQL 直接查询；会话/延迟类告警缺少入口视角。
- 修复（本报告同日落地，复用既有指标、零新增指标面）：
  - `platform/middleware/http_metrics.go`：`NewHTTPMetricsMiddleware(service)` —— statusRecorder 捕获最终写回码（含内层中间件改写后的码）+ `normalizePath` 把 UUID/数字/长随机段折叠为 `{id}`，保持 path label 低基数；计数进 `HTTPRequestTotal{service,method,path,status}`，延迟进 `HTTPRequestDuration{service,method,path}`。
  - `cmd/relay-gateway/wire.go`：以 `service="relay-gateway"` 挂入 routeMiddleware 链**最外层**（最后 append → 最先执行 → 看到最终状态码）；`/metrics`、`/healthz` 不经业务中间件，天然不产生 scrape 噪音。
  - 单测 `platform/middleware/http_metrics_test.go`：状态码捕获（含改写）、path 归一化、延迟观测、固定路由透传。
- 未来其他 HTTP 服务（admin/identity 等）如需入口指标，直接复用同一中间件（传各自 service 名），无需新建指标。

## 三、各议题触发后的执行入口（前置已就绪）

| 议题 | 触发后可执行性 | 备注 |
|---|---|---|
| 表分区 | ✅ 机制/DDL/runbook 全就绪 | 入口索引 `migrations/phase3_partitioning.sql` 指向按 schema 拆分的 logs / billing DDL 与 runbook；`logs` 按 Unix 秒 `RANGE(created_at)`、`billing_ledgers` 按 `TO_DAYS(created_at)`，运行时维护边界与各自 DDL 一致；**A+M1（2026-08-13 修正实施）**使用非分区 `billing_ledger_dedupe_claims` 主键在同一事务内原子 claim，`CreateLedgerInTx` 冲突返回 `ErrLedgerDedupeExists`，再由 `isDuplicateKeyError` 映射 `ErrDuplicateRequest`；账本分区默认不自动删除历史数据 |

## 四、维护责任

- 新指标**复用**既有 `micro_one_api_http_requests_total` / `micro_one_api_http_request_duration_seconds`（service 维度区分服务），不新增指标面。
- `normalizePath` 为通用规则（UUID/数字/超长段 → `{id}`），**固定路由透传、model 名不折叠**；新增含可变段的入口路由时无需改动（自动归一化），有单测守护低基数。
- P3 议题的启动判定以本报告 §一 的触发条件为准；条件满足时再开独立 ADR，禁止跳过准入直接实施。
