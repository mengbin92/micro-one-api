# 计时摘要 SQL 容量定位与改进

开始：2026-10-18；续验：2026-10-19（Asia/Shanghai）。承接[首次 SQL 链路验收](build-timing-sql-acceptance-2026-10-18.md)。基线 `54e6425c`，工作分支 `codex/timing-sql-capacity`。48 小时生产观察由另一台电脑继续负责；本轮使用本机一次性数据库与 GitHub 独立 Linux/amd64 runner，未使用部署 DSN、更新生产配置或部署服务。

## 1. 反馈环与瓶颈定位

### 持续写入

先执行现有背压/丢失确认回归，验证队列饱和不会阻塞 HTTP，恢复后已接收摘要完整落库。再使用相同 HTTP/SSE、服务身份、Log gRPC、生产 service/usecase/repository 与完整迁移 SQL 路径，运行四组交替短测定位拐点。短测每模式 2 秒，有独立测试名，不能替代原四组、每模式 30 秒的正式门禁。

本机为 darwin/arm64；MySQL 8.0 测试容器为已有 amd64 镜像、1 CPU / 1 GiB，通过本机回环随机端口连接。因此以下数值只用于本机差分诊断，不与先前独立 Linux 构建机的绝对吞吐直接比较。

| 探针 | 结果 |
| --- | --- |
| 原实现，16 并发 | 四组摘要丢弃均为 0 |
| 原实现，32 并发 | 四组摘要丢弃均为 0 |
| 原实现，64 并发 | 四组丢弃分别为 1160 / 1154 / 1117 / 1145；RPC P95 约 4.6–4.8ms |
| 只把 worker 从 2 改为 8 | 仍丢弃 740 / 766 / 735 / 810；RPC P95 增至约 36–43ms |
| SQL 语句计时 | 连接池等待为 0；每条摘要各执行 claim INSERT、log INSERT、refs INSERT、claim UPDATE |

由此优先改进逐条事务的摊销成本。增加并发本身没有消除瓶颈。语句计时来自可选的测试 GORM callbacks，不记录 SQL 文本、参数或用户内容；它不包含外层事务 commit 与 RPC 调度成本。

### 数据积累后的读取

第一版分组写入短测通过，但完整长测到第三、四组出现查询退化：最终 138,628 条摘要，第四组查询 P95 达到 2 秒、9 次查询失败，并伴随摘要丢弃。该次 FAIL 保留。

把问题缩小为 2,048 条合成摘要后，第一页 20 条结果需要读取 4,098 条索引记录。使用同一连接的 MySQL `Handler_read_*` 计数，避免依赖不稳定的耗时断言：

1. 仅把快照 `MAX(id)` 改为同过滤条件下的 `ORDER BY id DESC LIMIT 1`，读取降至 2,051。
2. 分页先通过覆盖索引取 ID，再按这些 ID 加载 JSON，读取降至 43。

16 个 worker 的原生中间版本：SQLite 64 并发长测无丢失；MySQL 第四组仍丢弃 264 条，PostgreSQL 三组仍有丢弃；三库 race 全部通过，完整容量结论仍未通过。随后在本机以相同 SQL 分组方案分别测量 32/64 个在途 RPC，两个方案四组短测均无丢失、有效批次约 20 条；该中间版本使用 64 个在途 RPC，把下一批已授权调用与当前组的 SQL/确认阶段重叠，事务快照上界仍为 32。

64 个在途 RPC 的初次原生对照仍有尾部丢弃：SQLite 第四组丢弃 1151 条，PostgreSQL 第二组丢弃 3208 条且有一次查询失败；这些 FAIL 继续保留。PostgreSQL 的 32 并发诊断记录了 835 次 log INSERT，有效批次约 6 条，表明固定 1ms 窗口碎片化，实际没有用足 32 条上限。本机差分探针中，改动后平均每批约 25.5 条，四组短测无丢失；继续保留短测不能代替原生长测的边界。后续改为满批信号唤醒，少量到达最多等 5ms，已积压的满批立即执行，避免对每批固定 sleep；队列和私有快照数量不变。

两步均保留完整授权、用户/时间/结果/预留过滤和快照 ID 上界。现有晚到记录、游标与撤权回归仍执行。该中间版本没有新增索引或迁移；后续冷统计补修新增 139 号迁移。

复查补充并发清理场景：若选中的整页在 JSON 加载前被保留期清理，原两阶段实现会返回无法继续使用的游标。已用确定性回归复现，改为携带覆盖索引中的时间/ID 键推进游标；整页被清理时仍能继续翻页，原授权与快照过滤保留。SQLite/MySQL 三次 race 重复通过，索引读上界仍为 43。

### PostgreSQL 完整链路定位

仅优化收集窗口仍不能使 PostgreSQL 完整门禁通过。独立诊断保持相同 4 CPU / 1 GiB 客户端、1 CPU / 512 MiB 数据库预算，记录事务 begin/commit、语句 P95/P99、WAL/checkpointer 与 cgroup 计数：约 245 秒内数据库仅新增约 0.65 秒 CPU 限流，客户端未限流。

默认缓存计划对照中，claim 顺扫读取 15,237,453 行，claim 查询/更新 P99 约 21.4/22.3ms。事务内强制自定义计划把两者降到约 1.3/1.7ms，但仍有 193 条丢弃，未计作通过。该设置只是诊断对照，未加入生产代码。prepared_statements 只保存带占位符的 SQL 形状，不含绑定值。相关语义参见 [PostgreSQL plan_cache_mode 官方说明](https://www.postgresql.org/docs/18/runtime-config-query.html#GUC-PLAN-CACHE-MODE)。

后续 PostgreSQL 专用写入改为在 claim INSERT 中使用现有 logs 序列预分配最终 ID，INSERT RETURNING 直接返回新键/ID。正常写入仅需 claim、log、refs 三次插入，去除热路径 claim 读取与二次更新；重放才读取既有 claim。claim → log → refs 锁顺序与旧写入路径一致，所有记录仍在一个事务中提交或回滚，序列回滚留下的 ID 间隙与常规 SERIAL 行为一致。新增“新 claim 无需读取/改写”和新旧写入路径并发去重回归，以及恢复旧路径的负向对照。

PostgreSQL 结构改造的独立验证 [39173067362](https://github.com/mengbin92/micro-one-api/actions/runs/39173067362) 中，默认计划四组丢弃 0 / 0 / 967 / 0；新路径并发实库 race 与旧路径负向对照均符合预期，但容量门禁仍为 FAIL。默认组事务提交最大 343.89ms，自定义计划诊断组触及 2 秒期限。新 claim 的查改已去除，但提交尾部停顿仍会填满有限队列，不能把功能正确性等同于容量通过。

随后三库 [39173453064](https://github.com/mengbin92/micro-one-api/actions/runs/39173453064) 全部容量 FAIL：SQLite 丢弃 3239 / 2567 / 7995 / 2080，MySQL 220 / 0 / 0 / 244，PostgreSQL 0 / 3894 / 0 / 2622，后者另有两次查询失败。该源码的普通 CI、安全和全部 E2E 均通过，仍未合并。

本轮把分组上限由 32 提到 128，同时以 256 个工作协程流水处理两组；队列仍为 256，导出器总保留上界相对上一候选由 320 增至 512（develop 原始上界为 2 + 256 = 258），Log 私有快照由 32 增至 128。这是明确的有界资源预算调整，用于摊销持久提交并在短暂停顿后赶上负载；不调整 SQL 持久化等级、RPC/事务超时或容量门禁。新增正式迁移数据库上的最大分组重放回归和 SQLite 覆盖索引查询计划检查。一次临时探针误用仅 AutoMigrate 的辅助库、缺失正式覆盖索引，已排除该错误假设，未向生产代码加入索引提示。

128 分组候选 [39176185333](https://github.com/mengbin92/micro-one-api/actions/runs/39176185333) 的 SQLite、MySQL 正式容量均通过，SQLite 三表各 149,216 条，MySQL 四组 P95 +1.82%–3.63%。MySQL 作业在后续 race 第十轮迁移建库时触及整套 5 分钟限额，已有 133 项测试通过、无断言失败或 DATA RACE；后续仅将整套运行时限调到 10 分钟，保留十次重复及全部业务/容量阈值。PostgreSQL 第二组仍丢弃 3,573 条并有一次查询超时，其他三组零丢失，整体仍 FAIL。

该次 PostgreSQL 数据库日志，以及前次 39173453064 日志，均精确指出获取快照的 `SELECT id ... ORDER BY id DESC LIMIT 1` 超时。把问题缩小为正式迁移库中的 2,048 条摘要，使用 PREPARE + force_generic_plan + EXPLAIN，旧查询估计动态时间范围仅匹配少量记录，选择时间索引扫描再按 id 排序；真实范围却覆盖全部计时记录。该回归在本机 PostgreSQL 16/18 均能确定性复现，不依赖耗时阈值。

最终快照先按完整授权、计时可见性与显式用户条件取水位，再把时间、结果、root、reservation 等检索条件应用到分页键和 JSON 加载。这样保留调用者可见范围和后续写入上界，避免动态时间参数参与水位计划，不读取全局无授权水位。PostgreSQL 18 实际计划变为 `logs_pkey` 倒序流式取首条；恢复旧源码的负向对照再次检出 Sort。新增越过搜索窗口但仍在本用户范围内的水位回归，明确验证授权和显式用户条件都不能包含其他用户；既有晚到写入、翻页撤权与保留期删除回归继续通过。force_generic_plan 只用于回归测试的独立连接，测试后 RESET，生产不设置该参数。

本机 SQLite、MySQL、PostgreSQL 18 的计时与查询 race 两次重复全部通过，耗时约 63 秒；完整单元回归 121 个包通过。当前正式原生复验源码 `b013ef06`，运行 [39177936355](https://github.com/mengbin92/micro-one-api/actions/runs/39177936355)。

`b013ef06` 的原生复验 [39177936355](https://github.com/mengbin92/micro-one-api/actions/runs/39177936355) 中，SQLite/MySQL 正式容量与十轮 race 全部通过，完整 CI、安全及 E2E 通过；PostgreSQL 仍在第二组快照超时、丢弃 3,852 条，第四组另丢弃 705 条，整体 FAIL。新库缺少统计信息时，即使移除了时间范围，通用计划仍会估计用户条件极有选择性，取时间索引后排序。早先仅在 ANALYZE 后检查计划漏掉了这个状态。

进一步用冷统计数据验证：单一 `(source,id,user_id)` 索引在 2,048 行通过，但扩至 65,536 行仍可能输给时间索引排序，该探针 FAIL 保留。最终 139 号迁移提供两个直接匹配顺序的索引：`(source,id)` 覆盖跨用户水位，`(source,user_id,id)` 覆盖单用户/权限范围水位；镜像迁移覆盖 MySQL/PostgreSQL/SQLite，并登记 Log schema 所有权，PO 的 AutoMigrate 元数据同步。关闭自动分析的 65,536 行正向探针通过，移除这两个索引的负向对照重新检出排序。正式回归同时检查冷统计/已分析、跨用户/单用户四种组合，不修改生产的分析或计划缓存配置。SQLite 从旧版本增量升级的回归也验证两个索引实际建立。

一轮本机 race 与迁移文件重命名重叠，读取已移除的临时路径失败，属于无效运行；最终迁移固定后重新执行，不把该轮当作通过。完整单元、迁移治理、架构、格式检查已通过。当前原生复验源码 `bde245f1`，运行 [39179783407](https://github.com/mengbin92/micro-one-api/actions/runs/39179783407)。

索引版 `bde245f1` 的 [39179783407](https://github.com/mengbin92/micro-one-api/actions/runs/39179783407) 已无 PostgreSQL 查询错误，前三组零丢失、四组 HTTP P95 +1.48%–1.95%；第四组 WAL 检查点同窗队列峰值触及 512，丢弃 3,087 条。结束时仅约 11.5ms 排空，说明不能只看平均处理能力，短时持久化停顿仍会填满有限暂存。MySQL 第四组另有 500 条丢弃、P95 +6.169%，该运行整体 FAIL，三库十轮 race 全部通过。旧失败没有重标为通过。

把排队症状缩小为四秒、64 路 HTTP、50ms 模拟处理、sink 前三秒暂停：原 256 队列丢弃 3,136 / 4,928；仅调整固定队列到 4,096 后，4,928 条全部导出，HTTP/摘要失败和丢弃均为零，恢复前积压 3,648 条、堆分配约 19.2MB。它验证缓冲预算，不是 SQL 容量准入；堆数值只针对小摘要夹具，不是最大输入内存保证。

最终保留 256 个 worker、128 份仓库快照、原 RPC/事务期限，把队列提高到 4,096，总保留上界为 4,352，约能暂存受控负载的三秒积压。代价是更高的峰值保留量和摘要可见延迟；生产仍需独立核对最大输入、峰值内存和 TTL/WS。新版原生流程在原正式门禁与十轮 race 后单独运行该暂停探针，保留 JSON/退出码；仍使用 4 CPU / 1 GiB 测量容器，并追加 race 后数据库日志。当前源码 `734dc3d1`、运行 [39181904005](https://github.com/mengbin92/micro-one-api/actions/runs/39181904005)。

## 2. 最终实现

- Relay exporter 队列固定为 4096；worker 固定为 256，每项仍最多尝试两次、每次超时 2 秒，关闭和丢弃计数保留。队列加在途的确定性背压上界为 4352（develop 原始上界 258）。
- Log data 层按仓库实例合并同时到达的计时摘要。每个实例最多持有 128 份快照，最多等待 5ms 收集一组、满 128 条立即提交；排空 goroutine 在空闲时退出。
- 每组在一个事务中处理去重 claim、摘要、attempt refs 与 claim ID 关联；PostgreSQL 新 claim 从插入时就持有最终 ID。去重键按固定顺序获取，重放沿用原始 ID 和摘要；同组重复键只写一份。
- 成功回复只在提交后产生。等待者取消不会取消同组其他调用；后台使用私有快照与独立 2 秒事务期限。取消后与成功提交竞争的重试仍由持久 claim 去重，调用方对象不会被后台修改。
- 计时之外的消费、审计、批量日志与收费路径沿用既有行为。公开 RPC、proto 与前端均未修改；139 号迁移只新增两个 logs 二级索引，不改数据列或记录。
- 分页快照水位保留完整授权、计时可见性和显式用户限制；时间、结果、root、reservation 条件在分页键与 JSON 加载时完整重用，水位只负责排除后续插入。生产不修改 PostgreSQL 计划缓存设置。
- 测量 JSON 增加完成到 sink 开始的队列等待 P95，以及 `accepted-exported-failed` 的峰值；后者包含在途项，不等同于纯队列长度。

## 3. 回归与证据边界

本机已完成：

- 整组关联写失败时，摘要、claim、refs 全部回滚，失败不暴露 ID。新回归已先在旧实现上复现部分提交。
- 两个仓库实例的交叠批次返回相同原始 ID；取消后的调用方修改不能改变已排队快照。
- 原有故障恢复、丢失确认重试、饱和时 HTTP 成功、摘要关联、可见范围、晚到游标和撤权检查。
- SQLite/MySQL 聚焦 race 重复回归，以及 Log 各层、requesttrace、Relay server 的完整相关测试。未提供外部 DSN 的 PostgreSQL 测试明确 skip，不计作实库通过。

本机 PostgreSQL 18 最终快照方案四组长测通过：145,097 条摘要三表一致，摘要丢弃/失败、HTTP/查询错误均为 0，P95 增量 +3.12% / +0.46% / +1.06% / +0.66%。数据库为原生 arm64 容器，1 CPU / 512 MiB；客户端 darwin/arm64、GOMAXPROCS=4，仍属于本机差分证据。

## 4. 原生验收方法

专用 workflow 使用三个独立 GitHub `ubuntu-24.04` runner，分别测试 SQLite、MySQL 8.0、PostgreSQL 18。在同一 runner 上顺序测量基线与候选：

1. 通过仓库 `make init` / `make proto` 生成忽略的桩，再在原生 Go 1.27.2/CGO 容器编译。编译阶段 4 CPU / 4 GiB，与测量分开。
2. 测量容器 4 CPU / 1 GiB、GOMAXPROCS=4、network=none。数据库只加入该容器网络命名空间并监听 loopback，不发布端口；MySQL 1 CPU / 1 GiB，PostgreSQL 1 CPU / 512 MiB。
3. 两个版本均执行 16、32 并发诊断点，再执行原 64 并发、四组交替、每模式 30 秒的完整门禁，保留全部退出码。候选必须摘要无丢弃/失败、三表计数一致、HTTP/查询无失败、每组 HTTP P95 增量不超过 5%，OTLP 完成/接收数一致。短诊断的 P95 超限保留原始非零退出码和 JSON，按诊断信息展示；摘要丢失、HTTP/查询错误、缺失或非法报告仍阻断，四组正式长测阈值不变。
4. 正式测量完成后再执行候选原生 race 回归，避免并行编译/测试干扰容量测量。
5. 保留 JSON、失败日志、容器状态与限额、硬件、源码和二进制摘要。测量进程用 runner UID 写入私有文件，上传前规范专用目录所有权。

可重复执行入口（仅独立 Linux/amd64 runner）：

```bash
TIMING_SQL_BASELINE=54e6425ce296db138362275fdcf7184d4d7f1608 \
TIMING_SQL_RESULTS=/tmp/timing-sql-results \
  bash scripts/benchmark/timing-sql-capacity.sh mysql
```
